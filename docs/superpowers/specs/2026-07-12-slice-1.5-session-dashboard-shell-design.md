# Slice 1.5 — Session & dashboard shell: design

**Date:** 2026-07-12
**Slice:** 1.5 (Phase 1 MVP)
**Status:** approved, pre-implementation

## Goal

Real login on the dashboard, a server-side session, and the authenticated app shell
reading data from the API with the user's token (PRD §7.6). After this slice a user logs
in through the dashboard, gets an httpOnly session, protected pages load API data with
their token, and logout clears the session.

This is the shell slice. **The API is the security boundary** (global `JwtAuthGuard`
deny-by-default + `ResourceGuard`); the dashboard's route protection is UX, not the gate.

- `apps/dashboard/src/lib/session.ts` — `Session` interface + `getSession()` returning `null` (stub).
- `apps/dashboard/src/lib/api-client.ts` — the only file that knows the API base URL
  (`${API_URL}/v1`); a `get<T>()` helper that fetches with a bearer token and **parses**

- `apps/dashboard/src/app/(auth)/login/page.tsx` — a plain HTML form POSTing to
  `/api/auth/login` (email + password). No error display.
- `apps/dashboard/playwright.config.ts` — `testDir: ./e2e`, `baseURL` from `E2E_BASE_URL`.
- API auth (all `@Public`, under `/v1`): `POST /auth/login`, `POST /auth/refresh`,
  `POST /auth/logout` — all take/return `TokenPair {accessToken, refreshToken, expiresIn}`.

- Contracts (`@timetrack/contracts`): `TokenPairSchema`, `JwtClaimsSchema {sub, role, teamId}`,
  `ProjectSchema` + `ListProjectsQuerySchema`, `UserSchema`, `TeamSchema`.
- Endpoints that exist **today**: `GET /projects`, `GET /users`, `GET /teams/current`,
  `GET /time-entries` (wired). `GET /reports/overview` does **not** exist (Slice 1.6).

  the normal path.

## The constraint that drives the design

Two facts combine to decide the architecture:

1. The API rotates refresh tokens **single-use, no grace window** — using a refresh token
   revokes it immediately. If a refresh succeeds but the rotated token is not persisted, the
   session dies on the next refresh.
2. In Next.js App Router, **Server Components can only _read_ cookies**; cookie _writes_ are
   legal only in Route Handlers, Server Actions, and middleware.

Therefore a lazy `getSession()`-based refresh is impossible: it would obtain a new access
token for the current render but be unable to persist the rotated refresh token. **Refresh
must live in a cookie-writable context.** We use a Route Handler (`/api/auth/refresh`).

## Session strategy (chosen: encrypted cookie + reactive refresh)

Decided with the user. No `middleware.ts`, no new dependency.

```
LOGIN     browser form POST ─► /api/auth/login (route handler)
          └► POST API /v1/auth/login ─► {accessToken, refreshToken, expiresIn}
          └► encrypt {accessToken, refreshToken, accessExpiresAt} ─► set httpOnly cookie
          └► 303 redirect ─► /   (on API 401: 303 ─► /login?error=1)

READ      Server Component ─► getSession() reads + decrypts cookie (never writes)
          └► valid + unexpired ─► Session {userId, role, accessToken}, fetch from API
          └► missing / invalid / expired access ─► null

GATE      (app)/layout.tsx: getSession() null ─► redirect('/api/auth/refresh')
          (a single path for both "never logged in" and "access token expired";
           the refresh handler is the one place that decides page-vs-login)

REFRESH   /api/auth/refresh (route handler — may write cookie)
          └► no cookie / decrypt fails ─► clear cookie ─► 303 ─► /login
          └► POST API /v1/auth/refresh {refreshToken}
          └► success ─► re-encrypt rotated pair ─► re-set cookie ─► 303 ─► /
          └► API 401 ─► clear cookie ─► 303 ─► /login

LOGOUT    /api/auth/logout ─► POST API /v1/auth/logout {refreshToken}
          └► clear cookie ─► 303 ─► /login
```

Route protection lives in **`(app)/layout.tsx`**: `getSession()` null → `redirect('/api/auth/refresh')`
(which reissues the session if the refresh token is still good, else falls through to `/login`).
Not in middleware (Next post-CVE-2025-29927 guidance: don't make middleware the auth gate).

## Design

### 1. `lib/session-cookie.ts` (new) — cookie + crypto

The single place that knows the cookie name, its shape, and the crypto. Keeps `session.ts`
and the route handler free of encoding details.

- **Cookie:** name `tt_session`; attributes `httpOnly, secure, sameSite: 'lax', path: '/'`,
  `maxAge` = refresh-token TTL in seconds (default 30d; a constant here — the dashboard does
  not read the API's `REFRESH_TOKEN_TTL`).
- **Payload:** `{ accessToken: string, refreshToken: string, accessExpiresAt: number }`
  (`accessExpiresAt` = epoch ms, computed at write time from the API's `expiresIn`).
- **Crypto:** AES-256-GCM via Node `crypto` (`webcrypto`/`crypto` available in the Node
  runtime the route handlers use). Key = SHA-256 of `DASHBOARD_SESSION_SECRET`. Format
  `base64url(iv).base64url(ciphertext+tag)`. Decrypt returns `null` on any failure (bad key,
  tampered ciphertext, malformed) — never throws to callers.
- **Exports:** `encryptSession(payload) → string`, `decryptSession(raw) → payload | null`,
  and small cookie helpers (`serializeSessionCookie`, `clearedSessionCookie`) returning the
  options object used with Next's `cookies()` API in route handlers.
- No secret, token, or plaintext payload is ever logged.

### 2. `lib/session.ts` — `getSession()`

`getSession()` is a **pure reader** (it cannot write cookies) returning the existing
`Session | null` type. `null` means "no usable access token right now" for **any** reason —
missing cookie, decrypt failure, invalid claims, or an expired access token. The layout maps
that single `null` onto `/api/auth/refresh`, which is the one place that decides whether to
reissue the session or fall through to `/login`. This keeps `null` unambiguous for callers.

- Read the `tt_session` cookie via `next/headers` `cookies()`. Missing → `null`.
- `decryptSession(raw)` → `null` on failure → return `null`.
- If `accessExpiresAt <= Date.now()` → return `null` (treated as "no usable session"; the
  layout's redirect to `/api/auth/refresh` reissues it if the refresh token is still good).
- Decode the access-token JWT **payload** (middle segment, base64url) and parse it through
  `JwtClaimsSchema`. Parse failure → `null`.
- Return `{ userId: claims.sub, role: claims.role, accessToken }`. No signature verification
  dashboard-side — the API verifies every call, and the cookie is httpOnly + encrypted, so
  its contents are not attacker-controlled.

### 3. `app/api/auth/[...auth]/route.ts` — login / logout / refresh

A catch-all route handler dispatching on the last path segment. Runs in the Node runtime.

- **`POST …/login`**: read `email`/`password` from `formData()` (the scaffold form posts
  urlencoded). `POST` API `/v1/auth/login`. On success: parse the response through
  `TokenPairSchema`, set the encrypted cookie, `303` → `/`. On API 401/validation error:
  `303` → `/login?error=1` (no cookie set). Never surface the API error body.
- **`GET …/refresh`**: decrypt the cookie; missing/undecryptable → clear cookie, `303` →
  `/login`. Else `POST` API `/v1/auth/refresh` with the stored refresh token. Success →
  re-set the encrypted cookie, `303` → `/`. API 401 → clear cookie, `303` → `/login`. (No
  `next`/return-path param — always land on `/`; avoids an open-redirect surface. Deep-link
  preservation is a deliberate non-goal for this shell slice.)
- **`POST …/logout`**: decrypt cookie; best-effort `POST` API `/v1/auth/logout` with the
  refresh token (ignore its result — logout is idempotent API-side); clear the cookie;
  `303` → `/login`.
- Any other segment → `404`.

### 4. `lib/api-client.ts` — add read methods (endpoints that exist today)

Add to the `api` object, each parsing through its contract schema:

- `listProjects(token, params) → Project[]` — `GET /projects` (`z.array(ProjectSchema)`).
- `listUsers(token) → User[]` — `GET /users` (`z.array(UserSchema)`).
- `getCurrentTeam(token) → Team` — `GET /teams/current` (`TeamSchema`).

**Deferred:** `teamOverview` — `GET /reports/overview` does not exist yet; it ships in
Slice 1.6. `phase-1-mvp.md` step 3 is updated in the same commit to say so.

### 5. `(app)/layout.tsx` — auth gate + shell chrome

- Server Component. `const session = await getSession(); if (!session) redirect('/api/auth/refresh')`
  (the refresh handler reissues the session or falls through to `/login` — see §3).
- Render the existing sidebar plus a small header showing the user's role and a **logout**
  control: a tiny form `action="/api/auth/logout" method="post"` with a submit button (no
  client JS). Keep the nav as-is.

### 6. `(auth)/login/page.tsx` — error display

- Keep the plain form POST to `/api/auth/login`. Read `searchParams.error` (Server
  Component) and render an inline "Invalid email or password" message when `error=1`.
  Drop the scaffold "wire this form" copy.

### 7. Env

- New `DASHBOARD_SESSION_SECRET` (≥32 chars) added to `.env.example` with a comment. The
  dashboard reads `process.env.DASHBOARD_SESSION_SECRET` directly (mirroring
  `api-client.ts`'s direct `process.env.API_URL`), not via `@timetrack/config` — that
  package validates DB/S3/JWT server secrets the dashboard must not hold. A missing/short
  secret fails fast in `session-cookie.ts` at first use.

## Testing

- **Unit (Vitest, no DB)** — `session-cookie.spec.ts`: encrypt→decrypt round-trip;
  `decryptSession` returns `null` on tampered ciphertext and on a wrong-key blob;
  `getSession()` returns `null` for a missing cookie, an expired `accessExpiresAt`, and a
  cookie whose JWT payload fails `JwtClaimsSchema`; returns the right `{userId, role}` for a
  valid cookie. (Cookie reads are stubbed; no Next server needed.)
- **E2E (Playwright, seeded)** — `e2e/session.e2e-spec.ts`: unauthenticated `GET /` →
  final URL `/login` (via the `/api/auth/refresh` → no-cookie hop; assert on the settled
  URL); submit the seeded admin credentials → lands on `/`; logout → back at `/login`, and
  `/` redirects again. Requires the API + a seeded admin running; document the prerequisites
  in the test file header.

## Verification (Done gate — driven, not just tests)

1. `docker compose -f infra/docker-compose.yml up -d` (postgres/redis/minio).
2. `pnpm db:migrate && SEED_ADMIN_EMAIL=… SEED_ADMIN_PASSWORD=… pnpm db:seed`.
3. Run API (`pnpm --filter api dev`) + dashboard (`pnpm --filter dashboard dev`) with
   `DASHBOARD_SESSION_SECRET` set.
4. In the browser: hit `/` → redirected to `/login`; log in → land on `/` with the shell;
   confirm a protected page fetches API data with the token; log out → back at `/login`.
5. `pnpm lint && pnpm typecheck && pnpm test && pnpm build` green.

## Out of scope (later slices)

- `teamOverview` / the overview screen content — Slice 1.6.
- Proactive/silent refresh via middleware — not needed for the shell; revisit if UX demands.
- Admin/users/settings screens — Slice 1.2's deferred dashboard work, after this slice.
- Any mutation flow from the dashboard (only reads here).

## Non-negotiables honored

- Browser never holds a long-lived token in JS: the token lives only in an httpOnly,
  encrypted cookie (PRD §7.6).
- No credential in `NEXT_PUBLIC_*`. No new dependency. Types come from `@timetrack/contracts`
  — no hand-written response interfaces. No secrets/tokens logged.
