# Slice 1.2 — Users & teams management (API)

**Status:** design approved (2026-07-12)
**Plan:** `docs/plans/phase-1-mvp.md` Slice 1.2 · builds on Slice 1.1 (invite/accept, seed admin, Testcontainers harness)

## Goal

An ADMIN manages the workforce over the API: deactivate/reactivate a user, and edit the team's monitoring policy. A user acknowledges the monitoring policy for **themselves**. Every mutation is audited. This slice introduces the **first `AuditLog` writers** in the codebase (today only a `findMany` read exists).

## Non-goals

- **No dashboard UI.** The plan's step 4 (admin/users, admin/settings pages) is **deferred to after Slice 1.5**. The dashboard cannot authenticate yet: `getSession()` returns `null`, `app/api/auth/[...auth]/route.ts` is a 501 stub, and "Session & dashboard shell" is Slice 1.5. A page built now could not call the API, so it could not be demonstrated end-to-end (the plan's own Definition of Done). This slice is API + contracts only. The plan's "from the dashboard" Done-when wording is corrected in the same commit that ships this slice to record the reorder.
- **No new schema/migration.** `User.deactivatedAt`, `User.monitoringAckAt`, `Team.settings`, `RefreshToken.revokedAt`, and `AuditLog` already exist. No `schema.prisma` change.
- **No new env vars.**
- No right-to-erasure (`admin.eraseUser` stays a scaffold — Phase 4).
- No audit-log UI (Phase 4).

## Decisions (resolved)

- **Scope: API-only; defer dashboard to after 1.5** (see Non-goals). User-selected.
- **Lockout guards on deactivate (both):** reject an admin deactivating **their own** account, and reject deactivating the **last remaining active ADMIN** on the team. Both surface as **409 Conflict** (a conflict with current state, consistent with the invite-duplicate 409 in Slice 1.1). Reactivate carries no lockout guard. User-selected.
- **`ackMonitoring` stays self-only via a hand-rolled check — deliberately NOT `@ResourceScope`.** CLAUDE.md §4 prefers annotation-based authz, but the global `ResourceAccessService` enforces _self / manager-of-team / admin_; applying it here would let an admin acknowledge on another user's behalf, violating PRD §4.1 "there is no admin override." This is the deliberate exception. The existing `if (userId !== actor.id) throw Forbidden` check is kept as-is.
- **Deactivate is one atomic transaction that also revokes refresh tokens.** Set `deactivatedAt`, `updateMany` the user's refresh tokens to `revokedAt = now()`, and write the `AuditLog` row — all in one `$transaction` inside `UsersRepository`. Token revocation is done **inline in that tx** rather than via a separate `AuthRepository` call, so the whole operation is atomic. `revokeAllForUser` is therefore **not** added to `AuthRepository`. Reactivate does **not** restore tokens; the user logs in fresh (existing refresh flow re-reads identity and would already reject revoked/expired tokens).
- **Settings update: merge, then validate the merged object through `TeamSettingsSchema`.** The `ZodValidationPipe` already range-checks each field of the partial patch, but the service re-validates the _merged_ object so defaults are filled and a partially-populated or legacy `{}` settings row still yields a complete, valid policy before it is written. A minor TOCTOU window exists on concurrent admin edits (read-merge-write is not serialized); acceptable for an admin-only, low-frequency operation and noted rather than locked.
- **Audit `diff` shapes:**
  - deactivate/reactivate → `{ deactivated: boolean }` (the new state; `action` names the operation).
  - ackMonitoring → `{ policyVersion }` (the acknowledged version; `monitoringAckAt` is the row timestamp).
  - updateSettings → `{ before, after }` (full settings objects).
- **Audit `action` strings:** `user.deactivate`, `user.reactivate`, `user.ack_monitoring`, `team.update_settings`. `targetType`/`targetId`: `user`/userId for the first three, `team`/teamId for settings.

## Components

### 1. Contracts — `packages/contracts/src/users.ts`

Add the body schema for `PATCH /v1/users/:id`:

```ts
/** PATCH /v1/users/:id — deactivate (true) or reactivate (false) a user. */
export const UpdateUserSchema = z.object({
  deactivated: z.boolean(),
});
export type UpdateUser = z.infer<typeof UpdateUserSchema>;
```

No other contract changes. `AckMonitoringSchema`, `UpdateSettingsSchema`, `TeamSettingsSchema`, `User`, `TeamSettings` are reused unchanged.

### 2. API surface & authorization

| Route                                                   | Guard                           | Resource authorization                                                                                    | Returns        |
| ------------------------------------------------------- | ------------------------------- | --------------------------------------------------------------------------------------------------------- | -------------- |
| `PATCH /v1/users/:id` `{ deactivated }`                 | `@Roles('ADMIN')`               | Actor's own team only (cross-team → **403**). On deactivate: self → **409**, last active admin → **409**. | `User`         |
| `POST /v1/users/:id/ack-monitoring` `{ policyVersion }` | authenticated (no role gate)    | **Self-only, hand-rolled** (other user → **403**). Not `@ResourceScope`.                                  | `User`         |
| `PATCH /v1/admin/settings` `<partial TeamSettings>`     | `@Roles('ADMIN')` (class-level) | Acts on the actor's own team (`actor.teamId`).                                                            | `TeamSettings` |

`PATCH /users/:id` uses `@Body(new ZodValidationPipe(UpdateUserSchema))` and `@CurrentUser()` — pipe scoped to the param, per CLAUDE.md §4.

### 3. Service / repository behavior

**`users.controller.ts`** — add:

```ts
@Patch(':id')
@Roles('ADMIN')
update(@Param('id') id, @Body(new ZodValidationPipe(UpdateUserSchema)) dto, @CurrentUser() actor)
  : Promise<User> { return this.service.setActive(id, dto, actor); }
```

**`users.service.ts`**

- `setActive(id, { deactivated }, actor)`:
  1. Load target (`repo.findForAdmin(id)` → `{ id, role, teamId, deactivatedAt }`); missing → **404**.
  2. Cross-team (`target.teamId !== actor.teamId`) → **403**.
  3. If `deactivated === true`:
     - `id === actor.id` → **409** ("cannot deactivate your own account").
     - target is **currently active** (`target.deactivatedAt === null`) AND is ADMIN AND it is the last active admin (`repo.countActiveAdmins(teamId) <= 1`) → **409** ("cannot deactivate the last admin"). The "currently active" clause prevents a false 409 when re-deactivating an already-inactive admin while exactly one _other_ admin is active.
  4. Call `repo.setActive(id, deactivated, actor.id)` (atomic tx below); return the resulting `User`.
  - Idempotency: deactivating an already-deactivated user (or reactivating an active one) is allowed and still writes an audit row; the guards above still apply to a deactivate call.
- `ackMonitoring(userId, dto, actor)`: keep the existing self-only `if (userId !== actor.id) → 403`. Replace the `NotImplementedException` with `return repo.ackMonitoring(userId, dto.policyVersion, actor.id)`.

**`users.repository.ts`** (Prisma only; one `$transaction` per mutation)

- `findForAdmin(id)` → `select { id, role, teamId, deactivatedAt }` or `null`.
- `countActiveAdmins(teamId)` → `count({ where: { teamId, role: 'ADMIN', deactivatedAt: null } })`.
- `setActive(id, deactivated, actorId)`:
  ```
  $transaction:
    user.update({ where:{id}, data:{ deactivatedAt: deactivated ? now : null } })
    if (deactivated) refreshToken.updateMany({ where:{ userId:id, revokedAt:null }, data:{ revokedAt: now } })
    auditLog.create({ actorId, action: deactivated ? 'user.deactivate' : 'user.reactivate',
                      targetType:'user', targetId:id, diff:{ deactivated } })
  ```
  Return the updated user projected to the `User` contract shape (reuse the existing row→User mapper).
- `ackMonitoring(userId, policyVersion, actorId)`:
  ```
  $transaction:
    user.update({ where:{id:userId}, data:{ monitoringAckAt: now } })
    auditLog.create({ actorId, action:'user.ack_monitoring', targetType:'user',
                      targetId:userId, diff:{ policyVersion } })
  ```
  Sole writer of `monitoringAckAt`. Return the updated user as `User`.
- Factor the row→`User` mapping (already inline in `listByTeam`) into a private helper so all three read paths share it.

**`admin.service.ts`**

- `updateSettings(patch, actor)`:
  1. `current = TeamSettingsSchema.parse(await repo.getSettings(actor.teamId) ?? {})` — normalize/default the stored value.
  2. `merged = TeamSettingsSchema.parse({ ...current, ...patch })` — validate the merged object (fills defaults, enforces ranges on the whole).
  3. `await repo.writeSettings(actor.teamId, merged, { before: current, after: merged }, actor.id)`.
  4. Return `merged`.

**`admin.repository.ts`**

- `getSettings(teamId)` → `select { settings }` (returns the raw `Json`), or team-missing handling (team always exists for a valid session; `null` → treated as `{}`).
- `writeSettings(teamId, settings, diff, actorId)`:
  ```
  $transaction:
    team.update({ where:{id:teamId}, data:{ settings } })
    auditLog.create({ actorId, action:'team.update_settings', targetType:'team',
                      targetId:teamId, diff })
  ```

No changes to `AuthRepository` or `TeamsRepository`.

## Tests (Vitest + Testcontainers, real Postgres/Redis — no mocked Prisma)

Service + integration coverage (80% gate on `apps/api`, `packages/contracts`):

- **deactivate**
  - deactivates a user, sets `deactivatedAt`, and **revokes the user's refresh tokens** (a previously valid refresh token no longer refreshes) ✓ + audit row `user.deactivate`.
  - cross-team target → **403**.
  - admin deactivating self → **409**.
  - deactivating the last active admin → **409**; deactivating an admin when another active admin exists → **200**.
  - missing user → **404**.
- **reactivate**
  - clears `deactivatedAt`; does **not** create new refresh tokens; audit row `user.reactivate`.
- **ackMonitoring**
  - self → **200**, sets `monitoringAckAt`, audit row `user.ack_monitoring` carrying `policyVersion`.
  - other user (incl. an admin targeting someone else) → **403** (the "no admin override" case).
- **updateSettings**
  - partial patch merges over current and **round-trips through `TeamSettingsSchema`**; unspecified fields keep prior values / defaults.
  - out-of-range value (e.g. `screenshotRetentionDays > 180`) → rejected (pipe **422**; merged-validation is the backstop).
  - audit row `team.update_settings` with `{ before, after }`.
- Each mutation asserts the expected `AuditLog` row exists (first audit coverage in the suite).
