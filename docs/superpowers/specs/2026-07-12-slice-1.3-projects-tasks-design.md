# Slice 1.3 — Projects & Tasks (design)

**Date:** 2026-07-12
**Branch:** `slice-1.3-projects-tasks`
**Plan:** [`docs/plans/phase-1-mvp.md`](../../plans/phase-1-mvp.md) §"Slice 1.3 — Projects & tasks"

## Goal

ADMIN/MANAGER create projects and tasks; everyone lists their team's projects for
assignment. Cross-team creation is rejected.

**Done when:** a manager creates a project with tasks; the client/dashboard can list them
for assignment; cross-team creation is rejected; archived projects are excluded from the
assignable list.

## Scope

**API + contracts only.** The projects dashboard pages (`projects/[projectId]`, list page)
are deferred to after Slice 1.5, which is where a working dashboard session lands — the same
call made for Slice 1.2's screens. This slice is verified end-to-end via curl.

## Current state (scaffold)

- `GET /projects` (`list`) is implemented and returns each team's projects with their tasks
  in one query (`include`). **No consumers yet** (the client is Slice 1.7; the dashboard is
  deferred) — verified by grep, so changing its default filter is safe.
- `createProject` / `createTask` throw `NotImplementedException`.
- `archive` is not wired.
- `CreateProjectSchema` / `CreateTaskSchema` / `ProjectSchema` / `TaskSchema` already exist
  in `packages/contracts/src/projects.ts`.

## Decisions

| Decision                        | Choice                                                          | Rationale                                                                                                                                                                         |
| ------------------------------- | --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Dashboard                       | Deferred to after 1.5                                           | Needs a session; consistent with 1.2                                                                                                                                              |
| Team ownership (create/archive) | **Own team only**, for BOTH MANAGER and ADMIN                   | Matches the `setActive` precedent (even ADMINs are same-team there)                                                                                                               |
| Audit                           | **All three mutations** write an `AuditLog` row                 | Consistent with 1.2 and the monitoring-software audit posture                                                                                                                     |
| List filter                     | Exclude archived by default; opt in via `?includeArchived=true` | Assignable list is non-archived; managers can still discover archived to un-archive                                                                                               |
| `includeArchived` by role       | **Honored for any authenticated team member**                   | Archived projects are the same team's and carry no sensitive fields; role-gating a param the assignable path never sends defends nothing and adds a surprising silent-drop branch |
| Cross-team existing resource    | `403` (not 404-to-hide)                                         | Matches `setActive`; settled, not re-litigated                                                                                                                                    |
| Query bool parsing              | `z.stringbool()` (Zod 4 native)                                 | `z.coerce.boolean()` turns `"false"` into `true`; `stringbool` parses `"true"`/`"false"` correctly                                                                                |

## 1. Contracts — `packages/contracts/src/projects.ts`

Existing schemas unchanged. Add:

```ts
export const UpdateProjectSchema = z.object({
  archived: z.boolean(),
});
export type UpdateProject = z.infer<typeof UpdateProjectSchema>;

// Query for GET /projects. z.stringbool() parses "true"/"false" correctly
// (z.coerce.boolean() would turn the string "false" into true). .default(false)
// makes .optional() redundant.
export const ListProjectsQuerySchema = z.object({
  includeArchived: z.stringbool().default(false),
});
export type ListProjectsQuery = z.infer<typeof ListProjectsQuerySchema>;
```

Export both from `packages/contracts/src/index.ts` if the barrel re-exports per-file (match
the existing pattern in that file).

**Contracts test** (`contracts.spec.ts`): assert `ListProjectsQuerySchema` parses
`includeArchived: "true"` → `true`, `"false"` → `false`, and absent → `false`. This is the
"test the schema through its real parse path" lesson (cf. the Zod-partial-defaults memory).

## 2. Endpoints — `apps/api/src/modules/projects/projects.controller.ts`

| Method  | Route             | Guard                       | Input                                                                       |
| ------- | ----------------- | --------------------------- | --------------------------------------------------------------------------- |
| `GET`   | `/projects`       | any authenticated           | `@Query(new ZodValidationPipe(ListProjectsQuerySchema))`                    |
| `POST`  | `/projects`       | `@Roles('MANAGER','ADMIN')` | `@Body(new ZodValidationPipe(CreateProjectSchema))`                         |
| `POST`  | `/projects/tasks` | `@Roles('MANAGER','ADMIN')` | `@Body(new ZodValidationPipe(CreateTaskSchema))`                            |
| `PATCH` | `/projects/:id`   | `@Roles('MANAGER','ADMIN')` | `@Param('id')` (uuid) + `@Body(new ZodValidationPipe(UpdateProjectSchema))` |

- Pipes are scoped to the parameter, never method-level `@UsePipes` (CLAUDE.md §4).
- **No `@ResourceScope`.** Projects are team-scoped, not user-scoped, so the global
  `ResourceGuard` (which resolves a `userId`) does not apply. Team ownership is asserted
  manually in the service. Add a one-line comment stating this reason (checklist item 6).
- `:id` param is validated as a uuid (via a `ZodValidationPipe(z.uuid())` on the param, or
  the existing param-validation convention in the codebase — match whatever `users`/`admin`
  do for `:id`).

## 3. Service — `apps/api/src/modules/projects/projects.service.ts`

The single authorization rule: **own-team-only for both MANAGER and ADMIN.**

- `list(user, query)`: `return repo.listByTeam(user.teamId, query.includeArchived)`.
- `createProject(dto, actor)`: if `dto.teamId !== actor.teamId` → `403`; else
  `repo.createProject(dto.teamId, dto.name, actor.id)`.
- `createTask(dto, actor)`: `const p = await repo.findForActor(dto.projectId)`; if `!p` →
  `404`; if `p.teamId !== actor.teamId` → `403`; else
  `repo.createTask(dto.projectId, dto.name, actor.id)`.
- `archive(id, dto, actor)`: `const p = await repo.findForActor(id)`; if `!p` → `404`; if
  `p.teamId !== actor.teamId` → `403`; else `repo.setArchived(id, dto.archived, actor.id)`.

403/404 bodies follow the RFC 9457 problem+json shape used across the codebase
(`type`/`title`/`status`), as in `users.service`.

## 4. Repository — `apps/api/src/modules/projects/projects.repository.ts`

Prisma lives here. Never select `*`.

- `listByTeam(teamId, includeArchived)`: add `archived: false` to the `where` unless
  `includeArchived` is true. Keep the existing `select` (id, teamId, name, archived, tasks)
  and `orderBy: { name: 'asc' }`.
- `createProject(teamId, name, actorId)`: `$transaction` → create project (return the
  `ProjectSchema` shape) + `auditLog.create({ actorId, action: 'project.create',
targetType: 'project', targetId, diff: { teamId, name } })`.
- `createTask(projectId, name, actorId)`: `$transaction` → create task + `auditLog.create({
action: 'task.create', targetType: 'task', targetId, diff: { projectId, name } })`.
- `findForActor(id)`: `select { id, teamId, archived }` — used for the cross-team check.
- `setArchived(id, archived, actorId)`: `$transaction` → update `archived` + `auditLog.create({
action: archived ? 'project.archive' : 'project.unarchive', targetType: 'project',
targetId: id, diff: { archived } })`. Return the updated `Project`.

No schema/migration change: `Project.archived` and the `@@index([teamId, archived])` already
exist in `schema.prisma`.

## 5. Tests

**Unit — `projects.service.spec.ts`** (mocked repo, no DB):

- cross-team `createProject` → 403 (repo not called).
- cross-team `createTask` → 403; missing project → 404.
- cross-team `archive` → 403; missing project → 404.
- `list` passes `includeArchived` straight through to the repo.

**Integration/e2e — `apps/api/test/projects.e2e-spec.ts`** (Testcontainers, real PG; located
in `apps/api/test/` to match `admin`/`invites`/`users`):

- MANAGER creates a project + a task, then `GET /projects` returns them.
- an archived project is excluded from `GET /projects` and included with
  `?includeArchived=true`.
- EMPLOYEE `POST /projects` → 403 (role guard).
- MANAGER creating a project for another team's `teamId` → 403.
- each mutation writes the expected `AuditLog` row.

Coverage gate 80% on `apps/api` and `packages/contracts` must hold.

## Verification (end-to-end, not just tests)

`pnpm lint && pnpm typecheck && pnpm test && pnpm build` green, then curl against a running

(with and without `?includeArchived=true`), `PATCH /v1/projects/:id`, and confirm a
cross-team create returns 403.
