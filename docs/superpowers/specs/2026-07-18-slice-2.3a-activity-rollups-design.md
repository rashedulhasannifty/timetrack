# Slice 2.3a — Activity rollups + summary read API — design

**Date:** 2026-07-18
**Phase:** 2 (Monitoring + transparency)
**Roadmap:** `docs/plans/phase-2-monitoring.md` §Slice 2.3
**PRD:** §6.3 (activity monitoring), §4.3 (symmetric transparency), §7.1.3 (worker), §11 (Phase 2 gate)

---

## 1. Goal & boundary

Turn the `activity_samples` that already flow in (ingested since 2.1) into **per-day
summaries** and expose them read-only. A repeatable worker job aggregates the previous
UTC day's samples per user into `avg activity %`, `active minutes`, and minutes-per-app /
per-category breakdowns; a new read endpoint serves those summaries under the same
self/manager/admin authorization as the samples list.

Slice 2.3 is decomposed into three independent sub-slices (mirrors 2.2a/b/c):

- **2.3a (this spec) — server/worker.** `ActivityDailySummary` model + migration, the
  `rollup-daily` processor, a net-new repeatable scheduler, and the
  `GET /activity-summaries` read endpoint + contract. No Swift, no dashboard UI.
- **2.3b — client capture.** `EventCounter` wiring (event **counts** only), app/window
  sampling, activity-% computation, client-side categorization from the
  `productiveApps`/`unproductiveApps` policy lists, and an activity sync engine.
- **2.3c — dashboard.** Activity-% chart + app/category breakdown on `/me` and
  `people/[userId]`, fed by the 2.3a summary endpoint.

**Full categorization** is the target for the slice, but it is produced **client-side in
2.3b**. In 2.3a the rollup aggregates by whatever `category` the samples already carry.
Until 2.3b ships, samples are `NEUTRAL`, so `byCategory` reads `{"NEUTRAL": n}` — the
rollup special-cases nothing.

**Done when:** a day of seeded `activity_samples` rolls up into one
`ActivityDailySummary` row per user (correct avg %, active minutes, `byApp`, `byCategory`),
a re-run is idempotent, and `GET /activity-summaries` returns those rows for the employee
(self) and their manager/admin — proven by integration + e2e tests against real Postgres;
the 403 cross-user case is tested; the 80%-functions coverage gate stays green.

## 3. Schema (`packages/db`)

New **non-partitioned** table — one row per user per day (row count = users × days, tiny
next to the partitioned `activity_samples`):

```prisma
/// Per-user daily rollup of activity_samples (PRD §6.3). Small, unpartitioned.
/// Idempotently upserted by the worker's rollup-daily job on (userId, day).
model ActivityDailySummary {
  userId         String
  day            DateTime @db.Date
  avgActivityPct Int
  activeMinutes  Int
  byApp          Json     // { "Xcode": 120, "Slack": 30 }  — minutes
  byCategory     Json     // { "PRODUCTIVE": 150, "NEUTRAL": 20 } — minutes

  @@id([userId, day])
  @@map("activity_daily_summaries")
}
```

- Follows the codebase's `userId`-without-FK convention (as `ActivitySample` does).
- Migration generated with `pnpm db:migrate` **in the same commit** as the schema change.
  A plain `migrate dev` scaffolds this correctly (no partial index / raw SQL needed).

## 4. Contracts (`packages/contracts/src/activity.ts`)

```ts
/** Per-day activity rollup (worker output; dashboard read). Minutes are integers. */
export const ActivityDailySummarySchema = z.object({
  userId: z.uuid(),
  day: z.iso.date(), // 'YYYY-MM-DD'
  avgActivityPct: z.number().int().min(0).max(100),
  activeMinutes: z.number().int().nonnegative(),
  byApp: z.record(z.string(), z.number().int().nonnegative()),
  byCategory: z.record(z.string(), z.number().int().nonnegative()),
});

/** Self-view / manager read window, bounded by from/to dates. */
export const ListActivitySummaryQuerySchema = z.object({
  userId: z.uuid().optional(),
  from: z.iso.date(),
  to: z.iso.date(),
});

export type ActivityDailySummary = z.infer<typeof ActivityDailySummarySchema>;
export type ListActivitySummaryQuery = z.infer<typeof ListActivitySummaryQuerySchema>;
```

- `byCategory` keys are `Category` values but typed as a string→int record (a partial map;
  absent categories are simply omitted). Keeping it `z.record(z.string(), …)` avoids Zod's
  full-enum-key requirement while the values stay validated.
- **Shared constant** `ACTIVITY_SAMPLE_INTERVAL_SECONDS = 60`, exported from contracts and
  consumed by the worker rollup. The Swift client (2.3b) hardcodes the same value with a
  comment pointing back here — Swift can't import the TS package, so the two must be kept
  in sync by convention.

## 5. Worker rollup (`apps/worker`)

Implement `RollupDailyProcessor.process(job)`:

1. **Target day (UTC):** `job.data.day` if provided (backfill / test hook), else the
   **previous** full UTC day. Day boundaries are UTC, matching 2.1's today-UTC convention.
2. **Fetch** `activity_samples` where `timestamp ∈ [dayStart, nextDayStart)` (UTC).
3. **Group by `userId`** and compute, per user:
   - `avgActivityPct` = `Math.round(mean(sample.activityPct))`.
   - `activeMinutes` = `totalSamples × ACTIVITY_SAMPLE_INTERVAL_SECONDS / 60`.
   - `byApp[app]` = `countForApp × ACTIVITY_SAMPLE_INTERVAL_SECONDS / 60`.
   - `byCategory[cat]` = `countForCat × ACTIVITY_SAMPLE_INTERVAL_SECONDS / 60`.
4. **Upsert** one `ActivityDailySummary` per `(userId, day)` → re-running the same day is
   idempotent (no duplicates, values overwritten).
5. A day with **no samples** produces **no rows** (nothing to upsert).
6. **Logging:** counts, `userId`, and `appName` only. **Never** `windowTitle`
   (already in the Pino redact list — keep it out of this code entirely).

Prisma lives only in the processor (worker's repository-equivalent), per `CLAUDE.md §3`.

## 6. Scheduler — net-new repeatable-job pattern (`apps/worker`)

A `RollupScheduler` provider implementing `OnApplicationBootstrap`:

- Injects the `rollup-daily` BullMQ queue (`@InjectQueue('rollup-daily')`).
- On boot, calls `queue.upsertJobScheduler('rollup-daily-cron', { pattern: '15 0 * * *', tz: 'UTC' }, { name: 'rollup', data: {} })`.
- `upsertJobScheduler` is idempotent, so every worker boot converges to a single
  scheduler (safe with multiple worker instances).
- Fires at **00:15 UTC daily**; the processor derives "previous UTC day" itself, so the
  job payload stays empty in normal operation.

This is the first repeatable job in the codebase; keep it small and obvious so 2.4 /
retention can follow the same shape.

## 7. Read API (`apps/api/src/modules/activity`)

New resource under the existing activity module (same domain, keeps the module cohesive):

- **`activity-summary.controller.ts`** — `@Controller('activity-summaries')`, one `@Get()`:
  - `@ResourceScope({ source: 'query', key: 'userId' })` (self / manager-of-team / admin,
    identical to the samples list — the rule stays in `ResourceAccessService`).
  - `@Query(new ZodValidationPipe(ListActivitySummaryQuerySchema))` (pipe scoped to the
    param, never method-level `@UsePipes`).
- **`ActivityService.listSummaries(query, user)`** — resolves `targetId = query.userId ??
user.id`, delegates to the repo. No Prisma here.
- **`ActivityRepository.listSummaries({ userId, from, to })`** — `findMany` where `userId`
  and `day ∈ [from, to]`, ordered by `day`, `select`-ing only the summary fields.
- Register the new controller in `activity.module.ts`.

Routes remain under `/v1` (global URI versioning). Response rows are shaped by
`ActivityDailySummarySchema`.

## 8. Redaction / logging

- `windowTitle` stays in the Pino redact list and never touches this slice's code paths
  (rollup reads `appName`, `category`, `activityPct` only; the summary never stores or
  logs titles).
- No new sensitive fields → no redact-list change needed. `appName`, minutes, and
  percentages are not sensitive.

## 9. Testing

**Worker (integration, real Postgres):**

- Aggregation correctness: seed a known day of samples for ≥2 users → assert
  `avgActivityPct` (rounded mean), `activeMinutes`, `byApp`, `byCategory` exactly.
- Category handling: samples across `PRODUCTIVE`/`NEUTRAL` roll into the right buckets;
  an all-`NEUTRAL` day yields `{"NEUTRAL": n}` (the pre-2.3b reality).
- Idempotency: run the same day twice → still one row per user, same values.
- Empty day: no samples → no summary rows written.
- Day boundary: a sample at `23:59:59Z` counts for that UTC day; `00:00:00Z` next day
  does not.

**API (e2e, seeded):**

- `GET /activity-summaries?userId=self&from&to` → **200**, own rows.
- Employee passing another `userId` → **403** (cross-user).
- Admin (scope) / manager-of-team → **200**.
- Unauthenticated → **401**. Missing/invalid `from`/`to` → **422**.

**Coverage:** the new worker processor + api read wire new code under the 80%-functions
gate; the integration/e2e tests above cover it (measured by `test:coverage`, not `test`).

## 10. Out of scope (later sub-slices)

- Client event counting, app/window sampling, activity-% computation, and client-side
  categorization → **2.3b**.
- Activity-% chart and app/category breakdown UI on `/me` and `people/[userId]` → **2.3c**.
- Self-healing multi-day backfill (only previous-day + manual re-run here), weekly
  rollups, and reports/CSV → out of scope / Phase 3.
