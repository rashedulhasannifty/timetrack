# Slice 1.6 — Team overview + timeline — Design

**Date:** 2026-07-12
**Plan reference:** `docs/plans/phase-1-mvp.md` § "Slice 1.6 — Team overview + timeline"
**PRD:** §6.5 (dashboard overview/timeline)

## Goal

The manager's first real screen: who is tracking now and today's hours per person, plus
a per-person timeline drill-down — all authorization enforced server-side. Plus the two
session-robustness fixes carried over from Slice 1.5.

## Scope

One branch, three logical commits:

1. `GET /reports/overview` (API + contracts) and its dashboard consumers (overview cards +
   person timeline).
2. Multi-tab refresh race — API grace window.
3. Claims-drift redirect loop-breaker — dashboard auth route.

Out of scope (documented follow-ups): timezone-aware "today" (UTC only for now); the
activity chart / activity-% (Phase 2/3).

## Commit 1 — API + contracts: `GET /reports/overview`

### Contract (`packages/contracts/src/reports.ts`, additive)

```ts
export const TeamOverviewQuerySchema = z.object({
  date: z.iso.date().optional(), // YYYY-MM-DD; absent → server's current UTC date
});

export const TeamOverviewRowSchema = z.object({
  userId: z.uuid(),
  name: z.string(),
  tracking: z.boolean(),
  trackedSecondsToday: z.number().int().nonnegative(),
});

export const TeamOverviewSchema = z.object({
  date: z.iso.date(),
  rows: z.array(TeamOverviewRowSchema),
});

export type TeamOverviewQuery = z.infer<typeof TeamOverviewQuerySchema>;
export type TeamOverviewRow = z.infer<typeof TeamOverviewRowSchema>;
export type TeamOverview = z.infer<typeof TeamOverviewSchema>;
```

Add exports to `packages/contracts/src/index.ts`.

### Route

`@Get('overview')` on `ReportsController`. The class carries `@Roles('MANAGER','ADMIN')`;
the overview handler declares its own **`@Roles('EMPLOYEE','MANAGER','ADMIN')`**. Because
`RolesGuard` resolves roles via `reflector.getAllAndOverride([handler, class])`, the
handler-level set wins, so an employee may call it (scoped to themselves).

```ts
@Get('overview')
@Roles('EMPLOYEE', 'MANAGER', 'ADMIN')
overview(
  @Query(new ZodValidationPipe(TeamOverviewQuerySchema)) query: TeamOverviewQuery,
  @CurrentUser() user: SessionUser,
): Promise<TeamOverview> {
  return this.service.overview(query, user);
}
```

### Service — scoping

- `EMPLOYEE` → a single row for themselves.
- `MANAGER` / `ADMIN` → every user on the **actor's own `teamId`**.

`ResourceAccessService` is per-target-user ("can actor touch user X"), not "list my team",
so it is not the right tool here. The service scopes by the actor's `teamId` directly. The
scope is never widened by any client parameter, so an employee cannot read the team and a
manager cannot read another team. **Write the 403/own-scope test**, not just the 200.

Resolve the effective date: `query.date ?? <current UTC date>`. Return it in the response so
the client renders the exact day the server computed.

### Repository — one raw query

Prisma's `groupBy` cannot express the interval clamping this needs, so use `$queryRaw`
(parameterized). Requirements the query must satisfy:

1. **Zero-entry members still appear.** Start from `users` for the scope and `LEFT JOIN`
   `time_entries` — a plain `GROUP BY` over `time_entries` would drop idle teammates.
2. **Running entries count live elapsed.** `COALESCE(end_time, now())`.
3. **Midnight-spanning entries clamp to the window.** With
   `day_start = date 00:00:00Z`, `day_end = date + 1 day`:
   `duration = EXTRACT(EPOCH FROM (LEAST(COALESCE(end_time, now()), day_end)
           - GREATEST(start_time, day_start)))`, and only count rows that overlap the
   window (`start_time < day_end AND COALESCE(end_time, now()) > day_start`). Floor any
   negative at 0.
4. **`tracking` from the same query:** `bool_or(end_time IS NULL)` (a row with no open
   entry yields `false`).

`trackedSecondsToday` is the summed, floored duration cast to an integer. One query, no N+1.

### Timezone

UTC day boundaries `[date 00:00Z, date + 1 day)`. No timezone field exists anywhere in the
system. **Documented limitation:** "today" flips at 00:00 UTC, which is mid-afternoon for US
teams. A tz-aware overview is a follow-up, not this slice.

### Tests

The aggregation lives in raw SQL, so its correctness is verified against a **real Postgres**
(Testcontainers integration), while **role/scoping** is verified in the service spec with a
mocked repository.

**Repository integration (real PG):**

- tracking flag true when a running entry exists, false otherwise
- today's sum includes a running entry's live elapsed
- a midnight-spanning entry is clamped to the day window
- a team member with zero entries appears with `tracking:false, trackedSecondsToday:0`

**Service spec (Vitest, mocked repo):**

- MANAGER/ADMIN query resolves the actor's `teamId`; EMPLOYEE resolves self-only
- scope is never widened by a client parameter → an employee's result is always self-only
  (the 403-equivalent — an employee cannot read the team)
- the effective date defaults to the current UTC date when `date` is absent

### Dashboard

- **`lib/api-client.ts`** — add `teamOverview(token, date?)`:
  `get('/reports/overview' + (date ? '?date=' + date : ''), TeamOverviewSchema, token)`.
- **`(app)/page.tsx`** — server component: `getSession()`, `api.teamOverview(token)`, render
  per-person cards (tracking dot + `formatHours(trackedSecondsToday)`), each linking to
  `people/[userId]`. Empty team → a friendly empty state.
- **`(app)/people/[userId]/page.tsx`** — fetch that user's entries via `listTimeEntries` for
  the same UTC day window and render the existing `<Timeline entries={…} />`. The API enforces
  the manager-owns-team rule; a 403 from the client surfaces as an empty/not-authorized state
  rather than a crash.
- If a duration/hours formatter does not already exist in `lib/format`, add a small
  `formatHours(seconds)` helper there (co-located with `formatTimeRange`).

## Commit 2 — Session fix: multi-tab refresh race (API grace window)

**Problem.** `auth.service.refresh()` does single-use rotation: it revokes the presented
refresh token before issuing a new pair. With 2+ dashboard tabs, once the access token
expires each tab's layout independently redirects to `/api/auth/refresh` with the same
cookie refresh token. The first request rotates it; the rest find it `revokedAt` and get a
401 → the dashboard logs the user out and the losing response clobbers the winner's cookie.

**Fix — a short rotation grace window at the API.**

- **Schema** (`packages/db/prisma/schema.prisma` + migration, same commit): add
  `RefreshToken.replacedById String?` (nullable self-relation). Set it on **rotation**
  (points at the successor token); leave it null on **logout** revocation. This is what
  distinguishes "rotated a moment ago, benign" from "revoked by logout / replayed".
- **Env** (`packages/config` + `.env.example`, same commit): add
  `REFRESH_GRACE_SECONDS` (default 10).
- **Service:** in `refresh()`, a token that is revoked is still accepted **iff**
  `replacedById != null` (rotation, not logout) **and**
  `now - revokedAt <= REFRESH_GRACE_SECONDS`. On that path, issue a fresh pair as normal
  (the successor's plaintext is not stored, so we mint a new one; the extra token is
  harmless and expires). A logout-revoked token (`replacedById == null`) or an out-of-grace
  token stays a hard 401.

**Security note.** The grace window opens a ~10s replay window for a stolen, already-rotated
refresh token — the standard refresh-rotation-with-grace tradeoff. Kept small and
configurable. Logout remains immediate (no grace).

**Tests (integration, real PG):**

- two concurrent `refresh()` calls with the same token → both succeed within grace
- a logout-revoked token → 401 even within the grace interval
- a rotation-revoked token past `REFRESH_GRACE_SECONDS` → 401

## Commit 3 — Session fix: claims-drift redirect loop-breaker

**Problem.** If the API ever issues an access token whose claims fail `JwtClaimsSchema`,
`getSession()` returns null → the layout redirects to `/api/auth/refresh` → refresh succeeds
but the **reissued** token still fails to decode → null again → a tight loop that burns one
refresh rotation per hop.

**Fix — in the dashboard auth route (`app/api/auth/[...auth]/route.ts`).** After a
successful `api.refresh`, decode and validate the new access token's claims before setting
the session. If it still cannot be decoded, **clear the session and redirect to `/login`**
instead of `/` — breaking the loop. Reuse a `decodeClaims` helper exported from
`lib/session.ts` (extract the existing private function).

**Test (dashboard):** a refresh that yields a claims-invalid access token lands on `/login`
with the session cleared, not in a redirect loop.
