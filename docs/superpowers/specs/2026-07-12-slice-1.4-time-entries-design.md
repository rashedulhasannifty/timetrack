# Slice 1.4 — Time entries (complete): design

**Date:** 2026-07-12
**Slice:** 1.4 (Phase 1 MVP)
**Status:** approved, pre-implementation

## Goal

Finish the server side of time tracking. Create (idempotent upsert on the client
UUIDv7) and list (with resource authorization) are already done. This slice adds:

1. **Edit past entries** via `PATCH /time-entries/:id`, writing an `AuditLog` row with a
   before/after diff and stamping `editedById` / `editedAt` (PRD §6.1).
2. The **"running entry"** concept the team overview (Slice 1.6) needs: a query for the
   active entry, and the invariant that a user has **at most one** running entry.

## Current state (what already exists)

- `time-entries.controller.ts` — `@Post()` upsert, `@Get()` list (`@ResourceScope({ source: 'query', key: 'userId' })`).
- `time-entries.service.ts` — `upsert` (attributes to the authenticated user), `list` (resolves target, defaults to self).
- `time-entries.repository.ts` — `upsert` (create/update on `id`), `list`, a `serialize` helper.
- `UpdateTimeEntrySchema` in `packages/contracts/src/time-entry.ts` — `CreateTimeEntrySchema.partial().omit({ id: true })`. **Reuse it; do not add a new contract.**
- `ResourceAccessService.assertCanAccessUser(actor, targetUserId)` in `common/authz/` — the single place the `self / manager-of-team / admin` rule lives. `AuthzModule` is `@Global`, so it is injectable anywhere with no new module import.
- Testcontainers harness `apps/api/test/db-harness.ts` (`startTestDb`, `truncateAll`) and repository-integration specs in `apps/api/test/*.e2e-spec.ts`, gated behind `RUN_E2E=1`.

## Design

### 1. `PATCH /time-entries/:id` — edit with audit

**Controller** — new `@Patch(':id')` handler:

- `@Param('id') id: string`
- `@Body(new ZodValidationPipe(UpdateTimeEntrySchema)) dto: UpdateTimeEntry` — pipe scoped
  to the param, never method-level `@UsePipes`.
- `@CurrentUser() actor: SessionUser`.
- **No `@ResourceScope`** — the target userId is not in the request, it is on the row, so
  the declarative `ResourceGuard` (which reads a userId from query/param) cannot resolve it.
  Authorization is enforced in the service via `ResourceAccessService` instead. Delegates to
  `service.edit(id, dto, actor)`.

**Service** — new `edit(id, dto, actor)`:

1. Reject an **empty patch** (no fields present) → **422** `UnprocessableEntityException`
   (nothing to edit; avoids a pointless audit row).
2. Fetch the entry via `repo.findForEdit(id)` → `{ userId, ...current fields }`. Missing →
   **404** `NotFoundException`.
3. `await this.access.assertCanAccessUser(actor, entry.userId)` — owner / manager-of-team /
   admin. Cross-team or non-owner → **403** (thrown by the access service). This reuses the
   one rule rather than re-implementing it; entries are user-scoped, which is exactly what
   `assertCanAccessUser` encodes.
4. Compute the changed-fields diff (see below) and call `repo.update(id, patch, actor.id)`.

The service gains a `ResourceAccessService` constructor dependency. No module change needed
(`AuthzModule` is `@Global`).

**404 vs 403:** follows the projects precedent — existing-but-cross-team → **403**, missing
→ **404**.

**Repository** — new `update(id, patch, actorId)`:

- A `$transaction` that:
  - `tx.timeEntry.update({ where: { id }, data: { ...changedFields, editedById: actorId, editedAt: new Date() }, select: <existing select> })`.
  - `tx.auditLog.create({ data: { actorId, action: 'time_entry.edit', targetType: 'time_entry', targetId: id, diff: { before, after } } })` in the **same** transaction (CLAUDE.md §4).
- `before` / `after` contain **only the fields that actually changed** (PRD §6.1 — before/after diff).
- Returns the fresh row through the existing `serialize`.
- Also participates in the P2002 → 409 mapping for the reopen case (see §3).

### 2. Two update paths kept separate (correctness)

`time_entries` is UPDATEd by two distinct paths:

- **upsert-close** (existing) — the client syncs an `endTime` on a previously-open entry.
  Normal operation. **No audit row, no `editedById` / `editedAt` stamp.**
- **PATCH edit** (new) — a manual correction. **Audits and stamps.**

PATCH gets its own `update` method and does **not** route through `upsert`. Tests assert the
negative: an upsert-close writes no audit row and leaves `editedById` / `editedAt` null.

### 3. At-most-one-running-entry — partial unique index

An entry with `endTime = null` is "running". Invariant: **at most one running entry per
user.** Enforced at the database level (chosen for race-safety without blurring the
service/repo boundary).

**Schema + migration (same commit):**

```sql
CREATE UNIQUE INDEX time_entries_one_running_per_user
  ON time_entries ("userId")
  WHERE "endTime" IS NULL;
```

- Raw SQL in a generated migration — the same raw-DDL pattern used for the monthly
  partitions. `time_entries` is **not** partitioned, so a partial unique index is safe (no
  partition-key constraint to respect).
- Prisma cannot model a partial unique index declaratively; represent it in
  `schema.prisma` only insofar as Prisma supports (a comment noting the raw-SQL index), and
  rely on the migration for the actual DDL. Run through `pnpm db:migrate`; never hand-edit
  the committed migration.

**Repository — P2002 → 409:**

- The `upsert` create-path and the PATCH `update` reopen-path (a PATCH that sets `endTime`
  back to `null`) catch Prisma **P2002** and throw a `ConflictException` (**409**) — the
  invites precedent (`Prisma.PrismaClientKnownRequestError`, `code === 'P2002'`, caught in
  the repository). The global problem+json filter does not map Prisma errors and never leaks
  Prisma text, so the repository must translate.
- **Idempotency preserved:** a retried same-`id` POST hits the UPDATE branch (matched on
  `id`), so no new row is inserted and the index is not violated. Offline retries stay no-ops.

### 4. Active-entry query (backs Slice 1.6)

- **Repository `findActiveByUser(userId)`** → the running entry (`where: { userId, endTime: null }`)
  or `null`, using the existing `select` + `serialize`.
- **Service method** wrapping it (e.g. `findActive(userId)`), for the overview in 1.6. It is
  exercised by a repository-integration test now so it is not uncalled code (CLAUDE.md §6).
- No endpoint is wired in this slice — the overview route lands in 1.6.

## Testing

**Deviation from Phase-1 plan item 4 (deliberate):** the plan text describes an HTTP/JWT
supertest suite (`GET self → 200`, `GET other → 403`, etc.). No HTTP-level e2e harness exists
in this repo; the convention that emerged from Slice 1.0 onward is **repository-integration**
tests in `apps/api/test/*.e2e-spec.ts` against a real Postgres (Testcontainers), plus
**service-unit** tests for authorization and business logic. This slice follows the
established convention, not the stale plan text.

- **Delete** the stale gated scaffold `apps/api/src/modules/time-entries/time-entries.e2e-spec.ts`
  — its entire premise (build a Nest HTTP app, mint JWTs, supertest) contradicts the
  convention and there is no harness for it.

**`time-entries.service.spec.ts` (unit, no DB):**

- `edit` calls `assertCanAccessUser` with the **fetched entry's `userId`** (owner passes;
  cross-team → 403 propagated from a stubbed access service).
- `edit` → **404** when the entry is missing.
- `edit` → **422** on an empty patch.
- Diff generation: only fields that changed appear in `before` / `after`.

The self / manager / admin **rule** itself remains tested in `resource-access.service.spec`
(exists) — not re-tested here.

**`apps/api/test/time-entries.e2e-spec.ts` (repo integration, `RUN_E2E=1`, real Postgres):**

- Double-upsert the same `id` → **one row** (idempotent, PRD §7.5).
- `update` writes an `AuditLog` row (`action: 'time_entry.edit'`) and stamps `editedById` /
  `editedAt`.
- upsert-close writes **no** audit row and leaves `editedById` / `editedAt` **null** (the
  negative from §2).
- A second running entry for the same user → **P2002 → 409** (the index).
- `findActiveByUser` returns the running row, and `null` when none is open.

## Scope guardrails

- Do **not** touch the existing `GET` `@ResourceScope` (it works).
- Do **not** wire the overview/dashboard (Slice 1.6).
- No dependency changes, no major upgrades.
- One migration (the partial unique index), one new module dependency injection
  (`ResourceAccessService`, no new import — `@Global`). `UpdateTimeEntrySchema` already exists.

## Done when

Entries can be created idempotently, listed with correct authorization, and edited with an
audit trail; a user cannot have two running entries; and `findActiveByUser` backs the
overview — all covered by service-unit and repository-integration tests.
