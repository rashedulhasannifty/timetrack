# Slice 2.2c — Employee screenshot redaction UI (design)

**Date:** 2026-07-17
**Phase/slice:** Phase 2 (Monitoring + transparency), closes Slice 2.2's remaining "Done when" item —
_"employees can redact with a reason."_
**Scope:** dashboard only. No API, contract, worker, or DB changes.

---

## 1. Goal

Give an employee a way, from their own self-view (`/me` → Screenshots tab), to **redact** one of
their screenshots with a required reason. Redaction is the privacy escape hatch: it permanently
deletes the stored image bytes and leaves a **tombstone** the manager still sees ("redacted by
employee: <reason>") — never a silent disappearance.

The server side already exists and is unchanged; this slice is the missing UI that reaches it.

## 2. Existing server contract (unchanged — for reference)

- `POST /v1/screenshots/:id/redact`, body `{ reason }` parsed by `RedactScreenshotSchema`
  (reason is a non-empty string; `''` → 422).
- **Owner-only:** the service checks `row.userId === session.userId`; a manager/admin gets **403**
  (deliberately NOT `@ResourceScope` — a manager must not redact an employee's shot).
- **Effect:** marks the row `REDACTED` + `redactedReason` (audited in the repo tx), then deletes
  the raw + thumbnail storage objects. The row persists as a tombstone. Reads never presign a
  REDACTED row, so `url`/`fullUrl` are absent.
- **Idempotent:** redacting an already-REDACTED row returns the existing tombstone (no second
  audit row, no re-issued deletes). Ownership is still checked first.

## 3. Non-goals / out of scope

- No manager redaction (owner-only by design; the manager view already renders the tombstone via
  `redactedReason` and is unchanged).
- No new date-range control. The self-view is **today-UTC** (a pre-existing self-view limitation,
  tracked separately with the 1.6 timezone follow-up). Redacting older screenshots is out of scope
  for this slice.
- No contract/API/worker/DB changes.

## 4. Approach

Follow the existing admin-settings mutation pattern exactly: a `'use server'` **Server Action**
invoked from a small `'use client'` component. The access token is read server-side in the action
and never crosses to the browser (CLAUDE.md: no credential in `NEXT_PUBLIC_*`).

Component boundary: a single client component `ScreenshotsPanel` owns the grid, the per-tile inline
redact state, and tombstone rendering. The `/me` page stays a Server Component and passes it the
`shots` array plus the Server Action. (A per-tile `ScreenshotTile` split was considered and rejected
as over-splitting for a simple grid — YAGNI; extract later if it grows.)

## 5. Components & data flow

### 5.1 API client — `apps/dashboard/src/lib/api-client.ts`

Add one method, using the existing `send('POST', …)` helper (the same one `inviteUser` uses; it
attaches the bearer token, throws `ApiError` on non-2xx, and Zod-parses the response):

```ts
redactScreenshot: (token: string, id: string, dto: RedactScreenshot): Promise<Screenshot> =>
  send('POST', `/screenshots/${id}/redact`, dto, ScreenshotSchema, token),
```

(`RedactScreenshot`/`RedactScreenshotSchema` come from `@timetrack/contracts`; `ScreenshotSchema`
is already imported.)

### 5.2 Server Action — `apps/dashboard/src/app/(app)/me/actions.ts` (`'use server'`)

```ts
export async function redactScreenshotAction(
  id: string,
  reason: string,
): Promise<{ ok: true } | { ok: false; error: string }>;
```

- `getSession()`; if none → `{ ok: false, error: 'Not signed in' }`.
- Validate `RedactScreenshotSchema.safeParse({ reason })`; on failure → `{ ok: false, error: 'A reason is required' }`.
- `api.redactScreenshot(session.accessToken, id, { reason })`.
- On success → `revalidatePath('/me')` then `{ ok: true }` (revalidation re-renders the tile as a
  tombstone from fresh server data).
- On thrown API error → `{ ok: false, error: 'Could not redact — try again' }` (never leak raw
  error text). A 403 shouldn't occur for one's own shot but maps to the same inline error.

### 5.3 UI — `apps/dashboard/src/app/(app)/me/ScreenshotsPanel.tsx` (`'use client'`)

Props: `{ shots: Screenshot[]; onRedact: (id, reason) => Promise<ActionResult> }`.
Replaces the inline Screenshots JSX in `page.tsx`; the page passes `shots={shots}` and
`onRedact={redactScreenshotAction}`.

Per-tile rendering by status:

- **READY** (`url` present): thumbnail + a small "Redact" affordance. Clicking reveals an inline
  reason `<input>` + a ⚠ "permanently deletes this image" note + **Confirm** / **Cancel**. Confirm
  is disabled while the reason is empty or a request is in flight. On success the tile re-renders
  as a tombstone (via revalidation); on error, an inline message shows and Confirm re-enables.
- **REDACTED**: a tombstone tile — a "Redacted" badge + `redactedReason` + the capture time, no
  image, no control. Mirrors what the manager sees.
- **PENDING** (no image yet): timestamp + status text only, **no** redact control (nothing to
  delete).

Local state is per-tile: which tile has its reason field open, the reason text, in-flight flag,
and any inline error. No optimistic mutation — await the action, then let revalidation swap the
tile (simplest; matches the settings-form precedent).

## 6. Error handling

- Reads already degrade per-tab (`page.tsx` wraps each fetch in `.catch(() => [])`); unchanged.
- Redact failures surface **inline on the tile**, never as a page crash or a thrown boundary.
- The action returns a typed result rather than throwing, so the client renders errors
  deterministically.

## 7. Testing

- **Vitest (unit, no DB):**
  - Action: mocked `api-client` — success returns `{ ok: true }` and calls `revalidatePath('/me')`;
    empty/whitespace reason short-circuits to the required-reason error without calling the API;
    a thrown API error maps to the generic inline error (no raw text).
  - Panel: state logic — READY renders the redact control; REDACTED renders a tombstone with the
    reason and no control; PENDING hides the control; Confirm is disabled on empty reason.
- **Playwright (`*.spec.ts`, seeded data):** sign in as an employee with a READY screenshot →
  open Screenshots tab → Redact → enter a reason → Confirm → tile becomes a tombstone showing the
  reason. (Dashboard e2e files must be `*.spec.ts`, not `*.e2e-spec.ts`.)
- The **403 non-owner** path is already covered by the server e2e; this slice does not re-test it
  in the UI (the UI only ever redacts the session user's own shots).

## 9. Definition of done

- Employee can redact a READY screenshot from `/me` with a required reason; the tile becomes a
  tombstone showing the reason; the image bytes are gone (server deletes them).
- Empty reason is blocked in the UI (and 422 server-side as a backstop).
- No token in the browser; mutation goes through the Server Action.
- `pnpm lint && pnpm typecheck && pnpm test && pnpm build` green; the redaction `*.spec.ts` passes.
- Ticks Slice 2.2's remaining "employees can redact with a reason" item.
