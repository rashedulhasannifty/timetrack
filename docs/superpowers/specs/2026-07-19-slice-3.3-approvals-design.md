# Slice 3.3 — Timesheet approvals — Design

**Date:** 2026-07-19
**Phase:** 3 — Reporting + approvals (`docs/plans/phase-3-reporting-approvals.md` §3.3)
**PRD:** §6.5 (approvals)

## Goal

Managers approve or flag employees' **weekly** timesheets for payroll, with an audit trail;
employees see their own status; cross-team decisions are rejected. PENDING timesheets are
generated automatically each week by a scheduled worker job.

## Decisions (locked with the user)

1. **Generation = scheduled worker job.** A weekly BullMQ repeatable cron generates PENDING
   rows; mirrors the existing `RollupScheduler` precedent. (Not lazy-on-read, not manual.)
2. **Hours snapshotted at decision.** `totalSeconds` is written onto the row when the manager
   decides, pinning the payroll number even if entries are later edited. (Not computed live.)
3. **Re-decision allowed, always audited.** A decided timesheet can move APPROVED↔FLAGGED; each
   transition writes its own `AuditLog` row. (Not locked-after-first-decision.)
4. **Generation targets active users with >0 tracked seconds in the week** — skips zero-hour and
   deactivated users so the queue stays meaningful.
5. **The reviewer `note` is visible to the employee** — consistent with this product's
   employee-visibility stance.

## Data model

New enum and model in `packages/db/prisma/schema.prisma` (+ generated migration, same commit):

```prisma
enum ApprovalStatus {
  PENDING
  APPROVED
  FLAGGED
}

model TimesheetApproval {
  id           String         @id @default(uuid(7))
  userId       String         // the employee whose week this is
  periodStart  DateTime       // Monday 00:00:00 UTC (ISO week start)
  periodEnd    DateTime       // periodStart + 7 days (half-open [start, end))
  status       ApprovalStatus @default(PENDING)
  totalSeconds Int?           // snapshotted at decision; null while PENDING
  reviewerId   String?        // manager/admin who decided — scalar, like AuditLog.actorId
  note         String?        // reviewer note; visible to the employee
  decidedAt    DateTime?
  createdAt    DateTime       @default(now())
  user         User           @relation(fields: [userId], references: [id])

  @@unique([userId, periodStart])
  @@index([status])
  @@map("timesheet_approvals")
}
```

- `@@unique([userId, periodStart])` is a **full composite unique** (both columns non-null), so
  `prisma migrate dev` scaffolds it normally — this is **not** the partial-index landmine that
  needs hand-authored raw SQL. The upsert idempotency key is `(userId, periodStart)`.
- `reviewerId` is a **scalar** column with no Prisma relation (matches `AuditLog.actorId` /
  `TimeEntry.projectId` convention). Only `user` gets a relation — needed for `userName` in the
  list and `teamId` scoping. `User` gains the back-relation `timesheetApprovals TimesheetApproval[]`.
- Period is **ISO week**: `periodStart` = Monday `00:00:00.000Z`, `periodEnd` = `periodStart + 7d`,
  half-open `[periodStart, periodEnd)`.

## Generation (worker)

- `apps/worker/src/schedulers/timesheet.scheduler.ts` — `OnApplicationBootstrap` registers a
  repeatable job via `queue.upsertJobScheduler('timesheet-generate-cron', { pattern: '30 0 * * 1',
tz: 'UTC' }, { name: 'timesheet-generate', data: {} })`. Mirrors `RollupScheduler` exactly
  (idempotent across replicas). Queue name `timesheet-generate`, registered in `worker.module.ts`.
- `apps/worker/src/processors/timesheet-generate.processor.ts` — regenerates a **rolling lookback
  window of the last `LOOKBACK_WEEKS = 4` closed ISO weeks** (not just the single just-closed week).
  **Why a window, not one week:** this is an offline-first app — the macOS client buffers entries
  and syncs them late (a laptop offline all week syncs days later). A once-per-week generator that
  only looked at the just-closed week would silently omit any user whose entries arrive after that
  Monday's cron, and they would never appear in the manager's queue. Regenerating the last 4 weeks
  catches late syncs; 4 weeks bounds the work and stops the window from reopening long-settled
  payroll periods. (Optional `{ periodStart }` job payload targets one specific week for
  backfill/seed.)
- For each week in the window, for every **active** user (`deactivatedAt IS NULL`) with **>0**
  clamped tracked seconds in that week, **upsert-if-missing** a `PENDING` `TimesheetApproval` on
  `(userId, periodStart)`: create only when absent, **never** touch an existing row (so a decided
  row is never clobbered and a late-arriving entry can still add a previously-missing row).
- **`periodStart` must be byte-identical on every run**, or `@@unique([userId, periodStart])`
  silently duplicates. Derive it deterministically with `date_trunc('week', <ts> AT TIME ZONE 'UTC')`
  — Postgres `date_trunc('week', …)` is **Monday-start (ISO)**, which matches this design — yielding
  a clean midnight-Monday timestamp. The **same** derivation is used at decide time to locate the
  period. `periodEnd = periodStart + interval '7 days'`.
- The tracked-seconds computation reuses the slice-3.2 **whole-second clamped** duration SQL
  (`date_trunc('second', …)` on clamped edges), so a generated week's implied hours and a later
  decision snapshot agree.

## API — `apps/api/src/modules/approvals` (six-file vertical slice)

- `approvals.controller.ts`
  - `GET /approvals?status=&teamId=` — `@Roles('EMPLOYEE','MANAGER','ADMIN')`; param-scoped
    `ZodValidationPipe(ApprovalListQuerySchema)`. Delegates to the service, which resolves scope.
  - `POST /approvals/:id/decide` — `@Roles('MANAGER','ADMIN')`; `@Body(ZodValidationPipe(DecisionSchema))`.
  - No Prisma in the controller; no method-level `@UsePipes` (param-scoped pipes only).
- `approvals.service.ts` — business logic, no Prisma.
  - `list(query, user)`: EMPLOYEE → own rows only; MANAGER → own team (join `users.teamId`);
    ADMIN → any, or a specific `teamId`. Mirrors `ReportsService.resolveScope` semantics; a MANAGER
    passing another team's `teamId` → 403.
  - `decide(id, dto, user)`: load the timesheet; `ResourceAccessService.assertCanAccessUser(user,
timesheet.userId)` (self/manager-of-team/admin → 403 otherwise; EMPLOYEE already blocked by
    `@Roles`). Compute the period's clamped tracked seconds for `userId` over
    `[periodStart, periodEnd)`, then hand the repo the new status/note/reviewerId + totalSeconds.
- `approvals.repository.ts` — Prisma only.
  - `list(...)`: **one** scoped `$queryRaw` (never a per-row SUM loop) joining `users` for
    `userName`/`teamId` and computing each row's **live** `trackedSeconds` via a single
    grouped/lateral join to `time_entries` keyed by `(userId, periodStart..periodEnd)` — SUM of
    `date_trunc('second', …)` clamped durations, same expression as slice 3.2 — so a PENDING row
    shows the manager the week's current hours. Ordered by `periodStart DESC, userName ASC`.
    (`totalSeconds` is the row's stored snapshot, returned as-is — null until decided.)
  - `periodTrackedSeconds(userId, from, to)`: single `$queryRaw` SUM of `date_trunc('second', …)`
    clamped durations (same expression as slice 3.2), for the snapshot.
  - `decide(id, { status, note, reviewerId, totalSeconds })`: a `$transaction` that updates the
    row **and** creates the `AuditLog` row (`action: 'timesheet.decide'`,
    `targetType: 'TimesheetApproval'`, `targetId: id`, `actorId: reviewerId`,
    `diff: { from: prevStatus, to: status, note }`) — atomically, per CLAUDE.md.
  - `upsertPending(...)` / a generation helper is in the **worker** processor (Prisma allowed in
    `processors/`), not the api repo.
- `approvals.module.ts`, `approvals.service.spec.ts`, plus `apps/api/test/approvals.e2e-spec.ts`.

## Contracts (`packages/contracts/src/approvals.ts`)

```ts
export const ApprovalStatusSchema = z.enum(['PENDING', 'APPROVED', 'FLAGGED']);

export const TimesheetApprovalSchema = z.object({
  id: z.uuid(),
  userId: z.uuid(),
  userName: z.string(),
  periodStart: z.iso.datetime(),
  periodEnd: z.iso.datetime(),
  status: ApprovalStatusSchema,
  trackedSeconds: z.number().int().nonnegative(), // LIVE hours for the period, computed at list time (so a PENDING row shows current hours to decide on)
  totalSeconds: z.number().int().nonnegative().nullable(), // SNAPSHOT pinned at decision; null while PENDING
  reviewerId: z.uuid().nullable(),
  note: z.string().nullable(),
  decidedAt: z.iso.datetime().nullable(),
});

export const DecisionSchema = z.object({
  status: z.enum(['APPROVED', 'FLAGGED']), // PENDING is not a decision
  note: z.string().max(2000).optional(),
});

export const ApprovalListQuerySchema = z.object({
  status: ApprovalStatusSchema.optional(),
  teamId: z.uuid().optional(), // ADMIN filter; MANAGER may only pass their own (else 403)
});
```

Types inferred (`z.infer`), never hand-written. No default-injecting `.partial()` (avoids the
Zod-partial-defaults landmine). `DecisionSchema.status` deliberately excludes `PENDING`.

  components verified via typecheck/build.

## Authorization summary

- List: EMPLOYEE self-only; MANAGER own team; ADMIN any/`teamId` (MANAGER passing a foreign
  `teamId` → 403). Deny-by-default global `JwtAuthGuard` + `@Roles`.
- Decide: `@Roles('MANAGER','ADMIN')` gates EMPLOYEE; `assertCanAccessUser(actor, timesheet.userId)`
  enforces manager-of-team / admin, 403 otherwise. Write the 403 test, not just the 200.

## Testing

- **Schema/migration** committed in the same commit as the schema change.
- **Worker** (e2e vs real PG): one PENDING per active user with >0 tracked seconds per week across
  the 4-week window; deactivated + zero-hour users skipped; **re-run is idempotent** (seed a row,
  re-run generation, assert no second `(userId, periodStart)` row appears — guards the
  `periodStart` determinism); a decided row is never overwritten; a **late-arriving entry** for a
  past in-window week creates the previously-missing row on the next run.
- **API unit** (`approvals.service.spec.ts`, mocked repo): list scope resolution (employee self,
  manager team, admin any, MANAGER-foreign-teamId 403); decide computes + passes the snapshot;
  `assertCanAccessUser` 403 path asserts reject + repo not called.
- **API e2e** (`approvals.e2e-spec.ts`, real PG): `decide` updates status/totalSeconds/decidedAt/
  reviewerId **and** writes exactly one `AuditLog` row **in the same tx**; `(userId, periodStart)`
  uniqueness (P2002); re-decision writes a second audit row and updates the snapshot; list scoping.
- **Contracts** (`approvals.spec.ts`): accept a valid row/decision; reject `PENDING` as a decision;
  reject an over-long note.
- **Dashboard**: api-client URL/auth/body + view-transform units; page/route via typecheck+build.
- Coverage gate is `RUN_E2E=1 pnpm --filter api test:coverage` (functions ≥80%), plus
  `packages/contracts` ≥80%.

## Out of scope

- Monthly/bi-weekly periods (weekly only, per PRD).
- Notifications/emails on decision (no email side-effect this slice).
- A payroll export of approved timesheets (a later concern; slice 3.2 CSV covers raw entries).
- Bulk approve-all (single-row decisions only this slice).
