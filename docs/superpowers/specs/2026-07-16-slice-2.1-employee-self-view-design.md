# Slice 2.1 — Employee self-view (transparency) — design

**Date:** 2026-07-16
**Phase:** 2 (Monitoring + transparency)
**Roadmap:** `docs/plans/phase-2-monitoring.md` §Slice 2.1
**PRD:** §4.3 (symmetric transparency), §6.1/§6.5 (reads), §11 (Phase 2 hard gate)

---

## 1. Goal

Ship the `/me` transparency surface: an employee sees **everything** recorded about
them — time entries, activity %, screenshots, and idle events — through the **same**
API endpoints a manager uses, scoped to self.

This is the PRD §11 hard-gate prerequisite: **Phase 2 does not ship capture (2.2/2.3)
until this self-view ships.** 2.1 builds the full transparency read surface now, so the
moment capture lands the employee can already inspect it.

## 2. Current state (verified against the code, 2026-07-16)

Already built (no change in this slice):

- `GET /time-entries?userId=&from=&to=` — self / manager-of-team / admin scoping via
  `@ResourceScope({ source: 'query', key: 'userId' })` → global `ResourceGuard`.
- `GET /screenshots?userId=&from=&to=` — same scoping; service reads rows. Presigned
  `url` is intentionally absent until MinIO is wired in **2.2**.
- Prisma models `ActivitySample` (partitioned; `@@index([userId, timestamp])`),
  `IdleEvent` (`@@index([userId, startTime])`), `Screenshot` all exist.
- Dashboard components `Timeline` and `ActivityChart` (`{ label, activityPct }[]`) exist;
  `lib/session.ts` `getSession()` returns `{ userId, role, accessToken }`; `lib/api-client.ts`
  has the typed `get()` helper and `listTimeEntries`.

Missing — the real 2.1 work:

- **API:** `GET /activity-samples` read (only `POST /activity-samples/batch` ingest exists);
  `GET /idle-events` read (only `POST /idle-events` ingest exists).
- **Contracts:** `ListActivityQuerySchema`, `ListIdleEventsQuerySchema`.
- **Dashboard:** `(app)/me/page.tsx` is a scaffold; needs the four-tab self-view.
  `api-client.ts` needs `listActivitySamples`, `listIdleEvents`, `listScreenshots`.
- **Tests:** the self-scope 403 case per new read.

**No schema change, no migration** — both models and their indexes already exist.

## 3. API design

Two new read endpoints, each mirroring the existing `time-entries` list pattern exactly:
`@ResourceScope({ source: 'query', key: 'userId' })` on the controller, Zod pipe scoped to
`@Query`, `@CurrentUser` for the caller. `ResourceGuard` enforces self / manager-of-team /
admin **before** the handler runs — no per-route authorization code.

| Endpoint                | Query                   | Returns                                     |
| ----------------------- | ----------------------- | ------------------------------------------- |
| `GET /activity-samples` | `userId?`, `from`, `to` | `ActivitySample[]`, `orderBy timestamp asc` |
| `GET /idle-events`      | `userId?`, `from`, `to` | `IdleEvent[]`, `orderBy startTime asc`      |

Both are **bounded by the required `from`/`to` window** — a natural query cap, no unbounded
scan. The scoping semantics: an employee may pass only their own `userId` (or omit it → self);
a manager may pass a team member's id; an admin, anyone. Enforced by `ResourceGuard`, identical
to `time-entries`/`screenshots`.

### Layering (CLAUDE.md §3 — do not deviate)

- `activity`: add `list()` to `activity.controller.ts` / `activity.service.ts` /
  `activity.repository.ts`. Repo: `activitySample.findMany({ where: { userId, timestamp: { gte: from, lte: to } }, orderBy: { timestamp: 'asc' }, select: {...} })` — explicit `select`, never `*`.
- `idle-events`: add `list()` across its three files. Repo:
  `idleEvent.findMany({ where: { userId, startTime: { gte: from, lte: to } }, orderBy: { startTime: 'asc' }, select: {...} })`.
- Prisma stays only in `*.repository.ts`. Services hold the (trivial) orchestration; controllers hold HTTP + guards + pipe.

## 4. Contracts (`packages/contracts`)

- `activity.ts`: add
  `ListActivityQuerySchema = z.object({ userId: z.uuid().optional(), from: z.iso.datetime(), to: z.iso.datetime() })`.
- `idle.ts`: add `ListIdleEventsQuerySchema` (identical shape).
- **Read-row shapes reuse the existing schemas** — the array element for the activity read is
  `ActivitySampleSchema`, for idle is `IdleEventSchema`. **Decision:** we do **not** add `userId`
  to these read rows. Each list call is already single-user-scoped by the query param, so a
  per-row `userId` would be redundant. (`ScreenshotSchema` carries `userId` because it predates
  this pattern; we do not retrofit it here.)

## 5. Dashboard `/me` — full transparency surface

`(app)/me/page.tsx`, a Server Component:

1. `getSession()`; if null, return null (the `(app)` layout already redirects to `/login`).
2. Default window = **today, UTC** (`YYYY-MM-DDT00:00:00.000Z` .. `...T23:59:59.999Z`) — consistent
   with the Phase-1 `people/[userId]` page; timezone stays UTC-only (1.6 follow-up, unchanged here).
3. Every fetch scopes to `session.userId` (the self case of the shared endpoints).
4. **Four tabs:**
   - **Timeline** — reuse `components/timeline/Timeline` with the user's `TimeEntry[]`.
   - **Activity** — map `ActivitySample[]` → `ActivityChart` points (`{ label: time, activityPct }`).
   - **Screenshots** — a grid; **empty state** until 2.2 wires MinIO/presigned URLs (no rows exist yet).
   - **Idle** — a list of away periods with their `KEPT | DISCARDED | UNRESOLVED` resolution.
   - Each tab renders live data where it exists today and a correct empty state where capture
     isn't wired yet, so 2.2/2.3 light them up with no further `/me` work.
5. `lib/api-client.ts`: add `listActivitySamples(token, params)`, `listIdleEvents(token, params)`,
   `listScreenshots(token, params)` — each parses the response through the contract schema via the
   existing `get()` helper (an API that drifts fails loudly here).

Tab switching is a small client concern; the data fetching stays in the Server Component (fetch all
four, pass down). No long-lived token reaches the browser.

## 6. Testing

- **Unit (Vitest, service specs):** `activity.service.list` and `idle-events.service.list` — self
  returns own rows; the `from`/`to` window and ordering are passed through to the repo.
- **The 403 case per read (CLAUDE.md §4):** e2e (Testcontainers, `RUN_E2E=1`) mirroring the
  `time-entries` e2e — seed two users on different teams, mint JWTs, assert:
  - employee → own `userId` → 200 with their rows;
  - employee → another `userId` → **403** (ResourceGuard);
  - within the window bound, rows outside `[from, to]` are excluded.
- **Coverage gate** stays green — the new read paths on `activity`/`idle-events` are now exercised.
- The dashboard `/me` is verified by driving it (login → open `/me` → tabs render, empty states
  where expected). Playwright for `/me` stays a scaffold until seeded capture data exists (2.2/2.3),
  consistent with the 1.6 approach.

## 7. Out of scope (explicit)

- Screenshot **capture** / presigned URLs → Slice 2.2. The Screenshots tab ships as a working
  shell with an empty state.
- Activity **rollups** / `ActivityDailySummary` → Slice 2.3. The Activity tab renders raw samples.
- Idle **notifications** → Slice 2.4.
- No timezone work beyond UTC-only.

## 8. Guardrails (apply here)

- No new capture path; these are read-only endpoints behind the same guard chain.
- Nothing a manager can read that the employee cannot — this slice is precisely that symmetry.
- `windowTitle` stays redacted in logs (already in the Pino redact list); never logged by the read path.
- No `*` selects back to the client; explicit `select` on every repo query.

## Done when

An employee opens `/me` and sees their own time entries, activity %, screenshots (shell/empty until
2.2), and idle events — through the same endpoints managers use — with the cross-user 403 case tested,
and the green gate + coverage intact.
