# Slice 2.3c — Dashboard activity views — design

**Date:** 2026-07-18
**Phase:** 2 (Monitoring + transparency)
**Roadmap:** `docs/plans/phase-2-monitoring.md` §Slice 2.3, step 4
**PRD:** §6.3 (activity monitoring), §4.3 (symmetric transparency), §11 (Phase 2 hard gate)

---

## 1. Goal

Render the **daily activity rollups** (shipped in 2.3a server/worker + 2.3b client) on the
dashboard, closing out slice 2.3:

- the employee self-view `/me` Activity tab, and
- the manager person-view `people/[userId]`,

both reading the **same** `GET /activity-summaries` endpoint scoped to the target user, so a
manager sees exactly what the employee sees about themselves.

**Dashboard-only.** No schema, migration, contract, API, or macOS-client change.

## 2. Current state (verified against the code, 2026-07-18)

Already built (no change in this slice):

- **API:** `GET /activity-summaries?userId=&from=&to=` (`activity-summary.controller.ts`) —
  self / manager-of-team / admin via `@ResourceScope({ source: 'query', key: 'userId' })` →
  global `ResourceGuard`. Returns `ActivityDailySummary[]`.
- **Contracts:** `ActivityDailySummarySchema` = `{ userId, day (iso.date), avgActivityPct
(int 0–100), activeMinutes (int ≥0), byApp: record<string,int>, byCategory:
record<string,int> }`; `ListActivitySummaryQuerySchema` = `{ userId?, from: iso.date,
to: iso.date }`. `Category` enum = `PRODUCTIVE | UNPRODUCTIVE | NEUTRAL`.
- **Worker:** `rollup-daily` processor aggregates the **previous UTC day**'s samples into one
  `ActivityDailySummary` row per user, scheduled 00:15 UTC. `byApp`/`byCategory` are
  minutes-per-key partial maps.
- **Dashboard:** `Timeline`, `ActivityChart` (`{ label, activityPct }[]`, a recharts
  `LineChart`); `lib/api-client.ts` `get()` helper (parses through the contract schema);
  `lib/me-view.ts` (`toActivityPoints`); `/me` four-tab surface (`MeTabs`), `people/[userId]`
  (Timeline-only). Dashboard styling is **plain Tailwind** — the design-system tokens
  (`--prod`, `--accent`, …) are **not** adopted anywhere and are out of scope here.

Missing — the real 2.3c work:

- `api-client.ts`: `listActivitySummaries(token, params)`.
- A pure view-transform module + an aggregate-across-days computation.
- A per-day activity-% chart component (bar).
- An `ActivitySummaryPanel` rendering chart + apps breakdown + category mix.
- Wire it into `/me` (Activity tab) and `people/[userId]` (a second section).
- Unit tests for the transforms.

## 3. Data source & window

- **Endpoint:** `GET /activity-summaries?userId=&from=&to=` — dates (`YYYY-MM-DD`), not
  datetimes. No new authorization: `ResourceGuard` already enforces self / manager-of-team /
  admin identical to `activity-samples`.
- **Window: the last 7 days ending yesterday (UTC).** The rollup runs at 00:15 UTC for the
  _previous_ day, so **today never has a summary** — the window deliberately ends **yesterday**.
  `to = yesterday`, `from = yesterday − 6 days` (7 days inclusive).
  - Rationale: summaries are per-completed-day; a "today" window is always empty by
    construction. This is a rollup view, not a live view — the live intraday line stays a
    raw-samples concern and is explicitly **not** part of this slice (see §8).
- `api-client.ts`: add
  `listActivitySummaries(token, params): Promise<ActivityDailySummary[]>` →
  `get('/activity-summaries?…', z.array(ActivityDailySummarySchema), token)`. An API that
  drifts fails loudly at the parse, like every other read.

## 4. View transforms (`lib/activity-summary-view.ts`) — pure, unit-tested

No DB, no React; mirrors the `me-view.ts` pattern. Given `ActivityDailySummary[]` (the 7-day
window, possibly sparse) it produces:

1. **`toDailyActivityPoints(summaries, from, to)`** → one point **per calendar day in the
   window** `{ label: 'MM-DD' (or weekday), activityPct: avgActivityPct }` (the
   `DailyActivityPoint` shape, defined in `ActivityDailyChart.tsx`). Days with no summary
   render as `0` (a gap in tracking, shown honestly), so the axis is always the full 7 days,
   not just days with data.
2. **`aggregateApps(summaries, topN = 6)`** → sum `byApp` minutes across days, sort desc,
   take top N, each `{ name, minutes, pct }` where `pct` is share of the max app's minutes
   (for the proportional bar). Ties broken by name for stable ordering.
3. **`aggregateCategories(summaries)`** → sum `byCategory` minutes across days into
   `{ PRODUCTIVE, NEUTRAL, UNPRODUCTIVE }` (absent keys → 0) plus each category's share of the
   total, for the single proportion bar. Unknown keys (none expected) are ignored, not crashed.
4. **`totalActiveMinutes(summaries)`** → sum of `activeMinutes` (the headline number).

All four are total functions on possibly-empty / sparse input — an empty window yields empty
apps, all-zero categories, and a 7-point zero series (the empty state is decided by the panel,
not by these).

## 5. Components (existing plain-neutral style)

- **`components/charts/ActivityDailyChart.tsx`** (`'use client'`) — recharts `BarChart`, one bar
  per day, `YAxis` domain `[0,100]`, `fill` `#171717`. A bar chart is the honest representation
  of **discrete daily** values (the removed `ActivityChart` line was intraday). Owns and exports
  the `DailyActivityPoint` shape (`{ label: string; activityPct: number }`) — the type moves
  here from the deleted `ActivityChart.tsx`.
- **`components/activity/ActivitySummaryPanel.tsx`** (server-rendered; receives already-fetched
  `ActivityDailySummary[]` + the window) — composes:
  - headline: `{totalActiveMinutes}` active min over the window;
  - `ActivityDailyChart` (per-day activity %);
  - **Apps & sites**: top-N app rows, each a label + proportional bar + minutes
    (`font-variant-numeric: tabular-nums`);
  - **Category mix**: one horizontal proportion bar split PRODUCTIVE / NEUTRAL / UNPRODUCTIVE
    with a 3-item legend. Minimal fixed colors — green `#16a34a` (productive), neutral `#a3a3a3`
    (neutral), amber `#d97706` (unproductive) — inline, no token migration.
  - **Empty state** when the window has no summaries: "No activity recorded in the last 7 days."
    (same degrade-to-empty-panel pattern as `/me` today).

The panel is the single rendering unit used by both surfaces, so self and manager views are
byte-identical.

## 6. Where it renders

### `/me` — Activity tab (replace, don't add)

- `me/page.tsx`: **drop** the `listActivitySamples` fetch and the `toActivityPoints` mapping for
  the Activity tab; **add** `listActivitySummaries` over the 7-day-ending-yesterday window
  (self-scoped to `session.userId`), `.catch(() => [])` like the other tab fetches.
- The **Activity** tab panel becomes `<ActivitySummaryPanel summaries={…} from={…} to={…} />`.
- Timeline / Screenshots / Idle tabs stay **today-scoped and unchanged** — they keep their own
  today window. Only the Activity tab moves to the 7-day rollup window.
- **Dead-code cleanup (this slice makes them dead):** the Activity tab is the _sole_ caller of
  both `lib/me-view.ts` (`toActivityPoints`) and `components/charts/ActivityChart.tsx`
  (the intraday `LineChart`). Both — plus `me-view.spec.ts` — are **removed**; the
  `DailyActivityPoint` type moves to `ActivityDailyChart.tsx`. Git history retains the LineChart
  if a future live-intraday slice wants it (§8-out-of-scope).

### `people/[userId]` — add a second section (stacked, no tabs)

- Keep the page's structure: **Timeline first, then an Activity section below it** (agreed: no
  tabs on the manager page — the invariant is _same data through the same endpoint_, not
  identical chrome).
- Fetch `listActivitySummaries` for the target `userId` over the same 7-day window, alongside
  the existing `listTimeEntries`. A **403 on either** keeps the existing "You're not permitted
  to view this person." state for the whole page (manager-owns-team enforced by the API).
- Render the **same** `ActivitySummaryPanel`.

Both pages fetch in the Server Component and pass data down; no long-lived token reaches the
browser.

## 7. Testing

- **Unit (Vitest, no DB)** for `lib/activity-summary-view.ts`:
  - per-day series fills all 7 days incl. zero-filled gaps for missing days, correct labels;
  - `aggregateApps` sums across days, sorts desc, caps at top N, computes share-of-max, stable
    tie-break;
  - `aggregateCategories` sums the three categories, zero-fills absent keys, shares sum to
    ≤100 and to 100 when non-empty;
  - `totalActiveMinutes` sums; empty input → empty apps / all-zero categories / 7 zero points.
- **Component sanity:** `ActivityDailyChart` / `ActivitySummaryPanel` render without throwing on
  empty and on populated input (light render test, consistent with existing dashboard specs).
- **No new API/authz tests** — the endpoint + its 403 e2e already shipped in 2.3a and are
  unchanged; this slice adds no server surface.
- **Green gate + coverage** stay intact (`packages/contracts` untouched; dashboard is outside
  the 80% api/contracts gate but tests still run).

## 8. Verification (DoD requires end-to-end, not just tests)

Summaries only exist for **completed days that had samples and a rollup run** — so a naive demo
is empty and indistinguishable from a bug. Seed a real past-day summary first:

1. Seed `activity_samples` for **yesterday** (UTC) for a seeded employee — a spread of
   `appName` / `category` / `activityPct` across a few hours (via `db:seed` extension or a
   one-off script against the local scratch DB).
2. Run the `rollup-daily` processor for that day (enqueue the repeatable job / invoke the
   processor directly) to produce the `ActivityDailySummary` row — **or** insert the summary
   row directly for the demo. The exact seed path is finalized in the implementation plan.
3. Drive it in the browser: log in as the employee → `/me` → **Activity** tab shows the per-day
   chart + apps + category mix; log in as the manager → `people/[employeeId]` → same panel
   under the Timeline. Confirm cross-user `people/[otherId]` → the "not permitted" state (403).
4. Paste the real output / observations (no fabricated results).

## 9. Out of scope (explicit)

- **Live intraday activity line** from raw `activity_samples` — not this slice; summaries have
  no intraday shape by design. (The old raw-sample Activity view is _replaced_, per the 2.1 DoD
  note "renders raw activity_samples until 2.3 adds daily rollups.")
- **Design-system-token migration** (`--prod`/`--accent`/surfaces) — the whole dashboard stays
  plain Tailwind; only a minimal inline category palette is introduced.
- **Range picker / configurable window** — fixed 7 days (YAGNI).
- **Screenshots pipeline** (2.2), **idle notifications** (2.4), timezone work beyond UTC-only.
- Any change to Timeline / Screenshots / Idle behavior, or to the API / worker / contracts /
  client.

## 10. Guardrails (apply here)

- Read-only; no new capture path, behind the same guard chain as every other read.
- Nothing a manager can read that the employee cannot — the shared `ActivitySummaryPanel` on the
  same endpoint **is** that symmetry.
- `windowTitle` never enters this path: the summary endpoint returns only aggregate
  `byApp`/`byCategory` minutes — no titles — and nothing here logs.
- No `*` selects (server-side already `select`s); no new dependency (recharts present).

## Done when

An employee opens `/me` → **Activity** and a manager opens `people/[userId]` and both see the
last-7-days activity-% chart, top apps/sites, and category mix from the **same**
`GET /activity-summaries` endpoint scoped to that user; the cross-user 403 state holds; the
view-transforms are unit-tested; and the green gate is intact — demonstrated end-to-end against
a seeded past-day summary.
