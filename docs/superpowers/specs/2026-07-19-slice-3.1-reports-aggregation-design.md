## 1. Goal & scope

Turn captured data into per-user and per-project rollups for any date range, scoped to
what the actor may see.

**In scope:**

- Implement `GET /reports/team-summary?from=&to=[&teamId=&userId=]` — per-user tracked
  seconds + activity % over the range (currently a `NotImplementedException` stub).
- Add `GET /reports/projects?from=&to=[&teamId=&projectId=]` — tracked seconds per project
  across the visible scope.
- Add `ProjectSummarySchema` to `packages/contracts/src/reports.ts`.
- Build the `(app)/reports` dashboard: date-range picker + per-user table + per-project
  bar chart (Server Component fetching the two endpoints, MANAGER/ADMIN only).

**Out of scope (do not touch):**

- **CSV export** — that is slice 3.2. The existing `exportCsv` stub in `reports.service.ts`
  stays exactly as-is (`NotImplementedException`). The `GET /reports/export.csv` route is
  left untouched.
- **No schema change / migration.** Both source tables (`time_entries`,
  `activity_daily_summaries`) already exist. This slice adds zero Prisma models.
- **Deep drill-down filters** in the dashboard UI (per-user, per-project pickers). The API
  honors `userId`/`projectId` query params (they are already in `ReportRangeQuerySchema`),
  but the 3.1 dashboard ships only the date-range picker + an ADMIN team selector. Deeper
  filter UI is a cheap follow-up, deliberately held out to keep the slice reviewable.

**Non-goals guardrails (CLAUDE.md §1):** reports are aggregates of already-captured data;
this slice adds no capture, no new sensitive field, no `windowTitle` exposure. Symmetric
transparency holds — the per-user rollup a manager sees is the same aggregate the employee
could compute of themselves.

## 2. The core risk — two-source aggregate fan-out (designed out)

`team-summary` must report, per user, **two** numbers from **two** tables that are each
one-to-many on `userId`:

- tracked seconds — `SUM` over `time_entries`
- activity % — a weighted average over `activity_daily_summaries`

The tempting move is to extend the existing `overview` query (which single-`LEFT JOIN`s
`time_entries`) with a second `LEFT JOIN` to `activity_daily_summaries`. **That produces a
Cartesian product:** a user with 3 time entries and 2 daily-summary rows yields 3 × 2 = 6
result rows, so `SUM(duration)` is doubled and the activity average is tripled. The existing
single-join `overview` never hits this, so copying it forward hides the bug.

**Design decision:** aggregate each source in its **own CTE keyed by `userId`**, then join the
CTEs on `userId`. One query, no fan-out. Concretely:

```sql
WITH scope_users AS (            -- the users the actor may see, in this range
  SELECT u.id, u.name FROM users u WHERE <scope> AND <has-data-in-range>
),
durations AS (                   -- one row per user: clamped tracked seconds
  SELECT te."userId", FLOOR(SUM(<interval-clamp>))::int AS tracked_seconds
  FROM time_entries te
  WHERE te."startTime" < :to AND COALESCE(te."endTime", now()) > :from
  GROUP BY te."userId"
),
activity AS (                    -- one row per user: activeMinutes-weighted avg %
  SELECT ads."userId",
         ROUND(SUM(ads."avgActivityPct"::numeric * ads."activeMinutes")
               / NULLIF(SUM(ads."activeMinutes"), 0))::int AS activity_pct
  FROM activity_daily_summaries ads
  WHERE ads."day" BETWEEN :fromDate AND :toDate
  GROUP BY ads."userId"
)
SELECT su.id AS "userId", su.name,
       COALESCE(d.tracked_seconds, 0) AS "trackedSeconds",
       COALESCE(a.activity_pct, 0)    AS "activityPct"
FROM scope_users su
LEFT JOIN durations d ON d."userId" = su.id
LEFT JOIN activity  a ON a."userId" = su.id
ORDER BY su.name ASC
```

`projects` is **single-source** (`time_entries` grouped by `projectId`), so it has no
fan-out risk — a plain `GROUP BY` is correct there.

## 3. Aggregation semantics (locked decisions)

| Concern                                         | Decision                                                                                                                                                                                                                                                             |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **activity % over a range**                     | `activeMinutes`-**weighted** average: `round(Σ(avgActivityPct × activeMinutes) / Σ(activeMinutes))`, clamped to `0..100` int. A high-activity day outweighs a 20-minute day.                                                                                         |
| **User with tracked time but no activity rows** | `activityPct = 0` (via `COALESCE`). `TeamSummaryRowSchema.activityPct` is `int().min(0).max(100)` and **not nullable**, so a null would throw at `.parse()`. `0` is the contract-safe value.                                                                         |
| **Deactivated users**                           | **Included** if they have data in the range. Historical reports must stay accurate for people who have since left. This **deviates** from `overview`, which filters `deactivatedAt IS NULL` because it answers "who is tracking today." Do **not** copy that filter. |
| **Range → day mapping**                         | `from`/`to` are datetimes; `ActivityDailySummary.day` is a `date`. A daily summary is counted when its `day` falls in the inclusive UTC-date span `[date(from), date(to)]` — i.e. any UTC day the range touches.                                                     |
| **Tracked-seconds precision**                   | The interval clamp from `overview` is reused verbatim: `GREATEST(EXTRACT(EPOCH FROM (LEAST(COALESCE(endTime, now()), :to) - GREATEST(startTime, :from))), 0)`. Running entries clamp to `now()`; entries crossing the range boundary are trimmed.                    |
| **Null-project entries**                        | Roll into a single **"No project"** bucket (`projectId: null`, `name: "No project"`) so per-project hours reconcile with each user's total tracked time. Nothing silently disappears.                                                                                |

`has-data-in-range` for `scope_users`: a user appears in `team-summary` if they have **either**
a time entry **or** a daily-summary row touching the range (so an activity-only or
time-only user is not dropped). Users with no data in the range do not appear.

## 4. Contracts (`packages/contracts/src/reports.ts`)

- `ReportRangeQuerySchema` — **exists**, reuse. (`from`, `to` datetimes; optional `userId`,
  `projectId`, `teamId`.)
- `TeamSummarySchema` / `TeamSummaryRowSchema` — **exist**, reuse as-is
  (`{ userId, name, trackedSeconds, activityPct }`).
- **Add:**

```ts
export const ProjectSummaryRowSchema = z.object({
  projectId: z.uuid().nullable(), // null → the "No project" bucket
  name: z.string(), // project name, or "No project"
  trackedSeconds: z.number().int().nonnegative(),
});

export const ProjectSummarySchema = z.object({
  from: z.iso.datetime(),
  to: z.iso.datetime(),
  rows: z.array(ProjectSummaryRowSchema),
});

export type ProjectSummaryRow = z.infer<typeof ProjectSummaryRowSchema>;
export type ProjectSummary = z.infer<typeof ProjectSummarySchema>;
```

Types are inferred from the schemas; no hand-written interfaces. Add both to the
`packages/contracts` barrel (`index.ts`) and the `contracts.spec.ts` shape check if present.

## 5. API

### 5.1 Controller (`apps/api/src/modules/reports/reports.controller.ts`)

- `team-summary` route **exists** and already binds `ReportRangeQuerySchema` + `CurrentUser`.
  Keep it. It sits under the controller-level `@Roles('MANAGER', 'ADMIN')`.
- **Add** `GET /reports/projects` — same `@Roles('MANAGER', 'ADMIN')`, binds
  `ReportRangeQuerySchema` via `ZodValidationPipe` scoped to `@Query`, passes `CurrentUser`.
- No `@ResourceScope` on either route — see §6.

### 5.2 Service (`reports.service.ts`)

- Implement `teamSummary(query, user)`: resolve the visible scope (§6), delegate to the
  repository, `TeamSummarySchema.parse({ from, to, rows })`.
- Add `projects(query, user)`: same scope resolution, delegate, `ProjectSummarySchema.parse`.
- Leave `exportCsv` untouched.

### 5.3 Repository (`reports.repository.ts`)

- Add `teamSummary(scopeSql, from, to)` — the CTE-per-source query in §2. `from`/`to` bind
  as `timestamptz`; the activity CTE also derives `date(from)`/`date(to)` for the `BETWEEN`.
- Add `projects(scopeSql, from, to)` — single-source `GROUP BY` over `time_entries` with the
  same interval clamp, `LEFT JOIN projects` for the name, `COALESCE(p.name, 'No project')`,
  `GROUP BY p.id, p.name` (null projectId groups together). Return rows ordered by
  `trackedSeconds DESC`.
- Both take the scope as a `Prisma.Sql` fragment built by the service (mirrors the existing
  `overviewForTeam`/`overviewForSelf` split), so the SQL string stays parameterized — never
  interpolate raw ids.
- `BigInt`/`numeric` columns are coerced to `Number` before returning (as `overview` does).
- **Never** `SELECT` or return `windowTitle` (it is not in these tables anyway; noted for the
  grep-audit).

## 6. Authorization — the `overview` pattern, not `@ResourceScope`

Reports are **team-level aggregates**, not user-scoped self-view reads, so they use the same
mechanism `overview` already uses: method-level `@Roles('MANAGER', 'ADMIN')` + **in-service
scope resolution**. `@ResourceScope`/`ResourceGuard` (the `userId`-keyed self/team/admin
gate used by `/activity-summaries`, `/screenshots`, etc.) is **not** used here.

Scope rule, resolved in the service before any query:

- **No `teamId`/`userId` filter:** MANAGER → own team (`user.teamId`); ADMIN → all teams.
- **MANAGER passes a `teamId` that isn't `user.teamId`, or a `userId` not on their team** →
  **403** (deny by default). Do not silently narrow — reject.
- **ADMIN** honors any `teamId` / `userId` / `projectId` filter.
- `projectId` (projects report) narrows the group set; it does not widen scope.

The 403 path is a **required test**, not just the 200 path (CLAUDE.md §4).

Ownership check ("is this userId on the manager's team?") reuses the existing team-membership
lookup the codebase already has for manager scoping (the same one `overview`/`ResourceAccessService`
rely on); do not re-implement the rule. If a direct helper isn't reachable from the reports
service, resolve team membership via a repository lookup — but keep the _rule_ (self / manager-of-team
/ admin) in one place, per CLAUDE.md §4.

## 7. Dashboard (`apps/dashboard/src/app/(app)/reports`)

- **`page.tsx`** — Server Component (replaces the current scaffold placeholder). Reads
  `from`/`to` (and, for ADMIN, `teamId`) from `searchParams`, defaulting to the **last 7 UTC
  days**. Fetches `team-summary` and `projects` for the range via the existing dashboard
  api-client, then renders the panels. Manager/Admin is enforced by the API; the page renders
  what it is allowed.
- **Date-range picker** — a small `'use client'` component that writes `?from=&to=` to the URL
  (router push), triggering an RSC refetch. No client-side data fetching.
- **ADMIN team selector** — `'use client'`, writes `?teamId=`. Rendered only for ADMIN
  (MANAGER is locked to own team; the control is hidden for them).
- **Per-user panel** — a table: name · tracked time (`formatMinutes` helper, matching
  `ActivitySummaryPanel`) · activity % (the neutral bar idiom from `ActivitySummaryPanel`).
- **Per-project panel** — horizontal hours-per-project bars via a thin `'use client'` Recharts
  wrapper styled to match `ActivityDailyChart` (neutral `#171717`, `ResponsiveContainer`).
- **View transforms** — pure functions in `apps/dashboard/src/lib/reports-view.ts`
  (seconds→display, row shaping, empty-state detection), unit-tested in node-env Vitest
  (no jsdom — components are verified by typecheck/build, per the dashboard testing pattern).
- **Empty state** — "No data in this range." when both panels are empty.

## 8. Testing

**API (Vitest + Testcontainers, real Postgres — do not mock Prisma):**

- **Fan-out regression (discriminating test):** seed one user with **multiple** time entries
  **and multiple** daily-summary rows in the range; assert `trackedSeconds` equals the true
  sum (not multiplied by the summary-row count) and `activityPct` equals the correct
  `activeMinutes`-weighted value. This is the test that fails on a naive double-`LEFT JOIN`.
- Weighted-average correctness across ≥2 days with different `activeMinutes`.
- Tracked time but **zero** activity rows → `activityPct: 0` (and `.parse()` does not throw).
- Interval clamp: entry crossing `from`/`to`; running entry (`endTime = null`) clamps to now.
- Deactivated-with-data user **appears** in the range report.
- Projects: grouping by project; **"No project"** bucket for null `projectId`; per-project
  hours reconcile to the user's total tracked seconds.
- **Authorization (403):** MANAGER requesting another team's `teamId` (or a `userId` not on
  their team) → 403; ADMIN → 200 for any `teamId`; EMPLOYEE → 403 (route is MANAGER/ADMIN).
- Coverage: keep `apps/api` + `packages/contracts` ≥ 80% functions (the binding metric).

**Contracts (Vitest):** `ProjectSummarySchema` accepts a valid payload incl. a null-projectId
row; rejects a negative `trackedSeconds`.

**Dashboard (node-env Vitest):** `reports-view.ts` pure transforms — seconds formatting, row
shaping, empty-state detection. Components covered by typecheck/build.

**Live verification (Definition of Done, not just green tests):** seed a known multi-day,
multi-project, multi-user window; hit `team-summary` and `projects` as MANAGER (own team) and
ADMIN (any team), confirm the numbers by hand against the seed; confirm the 403 for a
cross-team MANAGER request; load `/reports`, move the date range, confirm the panels update.
