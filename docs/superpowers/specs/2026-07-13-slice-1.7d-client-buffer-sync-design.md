# Slice 1.7d — Offline buffer + sync — Design

**Date:** 2026-07-13
**Slice:** 1.7d (macOS client MVP — offline buffer + sync)
**Branch:** `slice-1.7d-client-buffer-sync`
**Predecessor:** 1.7c (automatic tracking — done, merged)

---

## 1. Goal & scope

Replace the in-memory `BufferStore` stand-in with a **hand-rolled, file-backed durable FIFO**, and
build a real one-way (client → server) sync that drains buffered **TimeEntry** records to
`POST /v1/time-entries` with exponential backoff. Sync is idempotent because every record carries a
client-minted UUIDv7 and the API upserts on it (a retried record is a no-op, not a duplicate). This
closes the 1.7 MVP loop: a signed-in employee can work offline for ≥24h and see entries sync exactly
once.

**In scope**

- `Storage/BufferStore` — rewrite the in-memory stand-in as a durable, file-backed FIFO: one atomic
  file per record under Application Support, kind-tagged, FIFO-ordered, age-pruned, with a `clear()`.
- `Sync/BackoffPolicy` — a pure exponential-backoff calculator (cap + jitter, reset on success).
- `Sync/TimeEntryUploader` — `POST /v1/time-entries` with the access token; `401 → refresh → retry once`.
- `Sync/SyncEngine` — rewrite the stub: a periodic timer that drains the buffer's `timeEntry` records
  through the uploader, removing each on confirmed success and backing off on failure.
- Wiring in `App/AppDelegate`: start the sync timer on ready; on sign-out do a best-effort final
  drain, then `clear()` the buffer (the cross-user integrity invariant, §4).
- Threading a `kind` tag through the buffer enqueue path (`TimeTracker`, `AutoTrackingCoordinator`).

**Out of scope (later slices / phases)**

- **GRDB / any new SwiftPM dependency.** The buffer is hand-rolled (decision §7.1), in keeping with
  the hand-rolled UUIDv7 and CLAUDE.md §2.
- **Idle-event sync.** There is no server idle-events endpoint yet (only `POST /v1/time-entries`).
  `IdleEvent` records stay in the durable buffer, tagged `idleEvent`, pruned by age; a later slice
  syncs them once an endpoint exists. 1.7d's `SyncEngine` drains `timeEntry` records only.
- **Crash-durability of an in-progress (still-running) span.** 1.7d buffers only *completed* records
  (as today). A crash mid-tracking still loses the live span. Deferred to its own follow-up.
- **Batching.** `POST /v1/time-entries` is a single-record idempotent upsert; records are sent one at
  a time. (`activity-samples/batch` and screenshots are Phase 2.)
- Activity-sample and screenshot sync (Phase 2).

## 2. Constraints (carried from 1.7a–c + CLAUDE.md/PRD)

- **No new SwiftPM dependency.** (CLAUDE.md §2, decision §7.1)
- **All API routes are under `/v1`.** The injected base URL already carries it; never break `/v1`.
  (CLAUDE.md §4)
- **Sync is one-way (client → server) and idempotent on UUIDv7.** The API upserts; a retried record
  is a no-op. (PRD §7.5)
- **Sync is NOT a capture path.** It transmits the employee's own already-recorded entries; it does
  not touch any capture hardware. So it is **not** gated by `AckGate` — it needs only a valid
  session. `AckGate` stays untouched and reserved for capture. (CLAUDE.md §1)
- **The menu-bar indicator is unaffected; no stealth, no kill switch.** Sync is a background drain;
  it does not change the always-visible indicator. (CLAUDE.md §1, PRD §4.2)
- **No secret ships in the client.** The uploader uses the injected API base URL + the session's
  bearer token.
- **Tests reach the module via `@testable import TimeTrack`**; client tests run via `swift test`
  from `apps/client-macos` with `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer`
  (CommandLineTools lacks XCTest), outside `pnpm test`.
- **Commits:** Conventional Commits, scope `client`, no AI attribution. (CLAUDE.md §0)

## 3. Architecture

The slice keeps the 1.7a–c shape: small units behind protocols, a thin `AppDelegate` that wires them,
logic kept out of I/O edges. The durable buffer replaces the in-memory stand-in; the sync path is
three focused units.

```
   1.7c producers                         BufferStore (durable, file-backed)
┌────────────────────┐  enqueue(id,kind,payload)  ┌───────────────────────────────────┐
│ TimeTracker (.time │ ─────────────────────────▶ │ Application Support/TimeTrack/buffer/ │
│   Entry)           │                            │  <createdAtMillis>__<kind>__<id>.json │
│ AutoTrackingCoord. │ ─────────────────────────▶ │  (content = raw payload bytes)        │
│   (.idleEvent)     │                            └───────────────┬───────────────────────┘
└────────────────────┘                            take(.timeEntry)│ ▲ remove(id) / prune / clear
                                                                  ▼ │
                        ┌─────────────┐   drain loop   ┌───────────────────┐
                        │ BackoffPolicy│ ◀── on fail ── │    SyncEngine     │
                        │ (pure)       │ ── delay ────▶ │  (timer + drain)  │
                        └─────────────┘                 └─────────┬─────────┘
                                                        upload(payload) │ ▲ UploadResult
                                                                        ▼ │
                                                          ┌───────────────────────────┐
                                                          │ TimeEntryUploader         │
                                                          │ POST /v1/time-entries      │
                                                          │ Bearer; 401→refresh→retry  │
                                                          └───────────────────────────┘
```

`SyncEngine` is started by `AppDelegate` once the user is ready. It drains only `timeEntry` records;
`idleEvent` records accumulate durably (pruned by age) until a future endpoint drains them.

## 4. Data flow, durability & the cross-user invariant

### Record format (no envelope)

Each buffered record is a single file:

- **Filename:** `<createdAtMillis>__<kind>__<uuidv7>.json` — carries FIFO ordering (createdAt prefix),
  routing (`kind` = `timeEntry` | `idleEvent`), and identity (the UUIDv7). Listing the directory
  yields order + kind + id **without reading file contents**.
- **Content:** the **raw payload bytes** the 1.7c producers already build — a `CreateTimeEntry`-shaped
  JSON for time entries, an `IdleEvent`-shaped JSON for idle events. What is stored is exactly what is
  POSTed; no wrapper to encode/parse.
- Collisions: same-millisecond records still differ by the UUIDv7 in the filename. Sort key is
  `(createdAtMillis, id)`.

### Durability

- **Atomic enqueue:** write to `<dir>/.tmp-<id>`, then `FileManager.moveItem` (rename) to the final
  name. Rename is atomic on a single volume, so a reader never sees a half-written record.
- **Crash-during-write recovery:** on `BufferStore` init, delete any leftover `.tmp-*` files (a crash
  between write and rename left them; the record was never durably enqueued).
- **Delete-after-confirmed-upload:** `remove(id:)` runs only after a 2xx from the uploader. A crash
  between upload success and remove re-sends the record next cycle — harmless (idempotent upsert).

### Retention / capacity

- **`prune(olderThan:)`** deletes records older than a max age (default **7 days**), run each sync
  cycle. This honors PRD §7.5's "≥24h capacity" as a *floor* (we keep well beyond 24h) while bounding
  the buffer so undeliverable records — and buffered `idleEvent` records with no endpoint yet — can't
  grow without limit. Delivered `timeEntry` records are removed immediately on success, so only stuck
  or endpoint-less records ever age out.

### Sync cycle (`SyncEngine.syncNow`)

1. `prune(olderThan: maxAge)`.
2. `let batch = buffer.take(kind: .timeEntry, limit: N)` (FIFO).
3. For each record, `await uploader.upload(payload)`:
   - `.success` → `buffer.remove(id:)`, `backoff.reset()`.
   - `.permanent(status)` (a non-401 4xx — e.g. 422 the server will never accept) → `buffer.remove(id:)`
     and **log** (drop the poison record so it can't wedge the queue).
   - `.transient` (network / 5xx) or `.authFailed` (a 401 that survived the refresh-retry) → **stop
     this cycle** and schedule the next attempt after `backoff.nextDelay(afterFailure:)`.
4. If the whole batch drained and more remain, continue; else wait for the next timer tick.

Sync runs whenever there is a valid session; offline simply yields `.transient` → backoff. It is
**not** gated by `AckGate` (§2): the records are the employee's own, already recorded.

### The cross-user invariant (load-bearing)

`CreateTimeEntry` carries **no `userId`** — the server attributes each upsert to `@CurrentUser` from
the bearer token. Therefore a record buffered by user A, if uploaded with user B's token, would be
attributed to **B**. The `BufferStore` is a single global store (not per-user). To prevent this:

- **On sign-out, `AppDelegate` does a best-effort final `syncNow()`, then `stop()`s the engine and
  calls `BufferStore.shared.clear()`.** Undelivered records are dropped rather than risk
  mis-attribution to the next user — the same fail-safe posture as 1.7b, which already clears
  `ProjectCache` and the `AckMarker` on sign-out. Sign-out is user-initiated, so a final flush is
  attempted first; anything that can't drain (offline) is discarded.
- Per-user buffer subdirectories (keyed by `userId`, like `AckMarker`) are a cleaner long-term
  alternative and are noted for a future slice, but are out of scope here (the buffered payloads
  don't carry a userId and the enqueue path would need it threaded through).

## 5. Upload result model & auth

```
enum UploadResult {
    case success               // 2xx — server upserted (idempotent)
    case permanent(Int)        // non-401 4xx — will never succeed; drop the record
    case transient             // network error / 5xx — retry later with backoff
    case authFailed            // 401 that survived one refresh-retry — stop; session likely invalid
}
```

`TimeEntryUploader.upload(_ payload: Data)`:

1. `let token = try await session.accessToken()`; `POST /v1/time-entries`, `Authorization: Bearer`,
   body = the raw payload bytes.
2. `200/201` → `.success`. `5xx` or a thrown network error → `.transient`. `401` → `session.forceRefresh()`,
   retry once; a second `401` → `.authFailed`. Other `4xx` → `.permanent(status)`.

This mirrors the established `PolicyClient`/`ProjectClient` 401-retry pattern; no new correlation id,
no new auth path.

`BackoffPolicy`: `base` (e.g. 5s) · `2^failureCount`, capped (e.g. 300s), with bounded jitter;
`reset()` on any success. Pure and deterministic under an injected jitter source for tests.

## 6. Testing

**XCTest (unit) — `@testable import TimeTrack`, `swift test` (with `DEVELOPER_DIR=<Xcode>`):**

- **`BufferStoreTests`** — `enqueue` writes exactly one file whose content equals the payload bytes;
  a leftover `.tmp-*` is swept on init and never surfaces in `take`; `take(kind:limit:)` returns only
  the requested kind, FIFO-ordered by createdAt, honoring `limit`; `remove(id:)` deletes just that
  record; `prune(olderThan:)` deletes records past the age and keeps fresh ones; `clear()` empties the
  directory; a temp directory + injected clock isolate each test (mirrors `ProjectCacheTests`).
- **`BackoffPolicyTests`** — delay grows exponentially with the failure count, never exceeds the cap,
  jitter stays within bounds (injected jitter source), and `reset()` returns to the base.
- **`SyncEngineTests`** (fake `Uploading` + a real temp-dir `BufferStore`) — drains buffered
  `timeEntry` records and removes each on `.success`; **leaves `idleEvent` records untouched**; on
  `.transient` stops the cycle with records still buffered and asks the backoff for a delay; on
  `.permanent` drops the poison record and continues; a record that "succeeds" on a retry is removed
  exactly once (idempotency); `prune` is invoked each cycle.
- **`TimeEntryUploader`** — build-verified; the `401 → refresh → retry-once → authFailed` decision
  logic covered as in `ProjectClient` (no live-network test).

**Manual smoke (end-to-end) — recorded, not fabricated:** with the API down, sign in (prior ack) →
track manual + auto → confirm record **files appear** under Application Support/TimeTrack/buffer/.
Bring the API up → confirm the files drain (POST 201) and are removed, with **no duplicates** on the
server (re-run to confirm idempotency). Kill the API mid-drain → confirm backoff, then recovery when
it returns. Sign out with undelivered records → confirm the buffer directory is cleared.

## 7. Decisions captured during design

1. **Buffer storage = hand-rolled file-backed FIFO (no dependency).** Deviates from PRD §7.5's GRDB;
   in keeping with the hand-rolled UUIDv7 and CLAUDE.md §2. Durability comes from atomic
   write-temp-then-rename + a startup `.tmp` sweep, not a SQLite engine.
2. **Sync scope = time-entries only.** No server idle-events endpoint exists; `idleEvent` records
   stay buffered (tagged, age-pruned) for a later slice. No api/db/contracts expansion this slice.
3. **Crash-durability of an in-progress span = deferred.** Buffer holds completed records only.
4. **`UploadQueue` folded into the durable buffer.** The file-backed `BufferStore` *is* the upload
   queue; the drain loop lives in `SyncEngine`. Deviates from PRD §7.5's separate `UploadQueue` file
   (fewer moving parts) — an as-built refinement.
5. **Sync is not gated by `AckGate`** (it's not a capture path) and **sign-out flushes-then-clears the
   buffer** to prevent cross-user mis-attribution (§4).

These as-built refinements (1, 4) should be reflected in PRD §7.9 when the slice lands.
