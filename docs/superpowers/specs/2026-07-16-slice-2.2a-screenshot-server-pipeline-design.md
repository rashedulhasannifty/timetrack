# Slice 2.2a — Screenshot server pipeline — design

**Date:** 2026-07-16
**Phase:** 2 (Monitoring + transparency)
**Roadmap:** `docs/plans/phase-2-monitoring.md` §Slice 2.2
**PRD:** §6.2 (screenshot capture), §7.4 (screenshot pipeline), §4.3 (symmetric transparency), §8 (presigned URLs), §11 (Phase 2 gate)

---

## 1. Goal & boundary

Ship the **server half** of the screenshot pipeline end-to-end: an image uploaded to
`POST /screenshots` streams straight to object storage, gets a `PENDING` row, is
processed by a worker into a thumbnail (+ optional blur), reaches `READY`, and is
readable through short-lived presigned URLs — with an owner-only redact path.

Slice 2.2 is decomposed (the §11 gate is **release-level**, not slice-level — self-view
and capture ship in the same _version_, not the same PR; mirrors the 1.7a–d pattern):

- **2.2a (this spec) — server pipeline.** API upload/read/redact + worker processing +
  integration tests. No Swift, no dashboard UI.
- **2.2b — client capture.** ScreenCaptureKit behind `AckGate`, durable binary buffer,
  delete-local-only-after-confirmed-201.
- **2.2c — dashboard.** Screenshot grid on `/me` + `people/[userId]`, redact button
  (fills the empty-state shell 2.1 already shipped).

**Done when:** a real image `curl`-uploaded flows `PENDING → READY` and returns as a
presigned URL, proven by integration tests running against a **real MinIO container**;
each blur mode produces the correct derivative; redact is owner-only and leaves a
tombstone row; the storage code clears the 80% coverage gate.

Production note: object storage is **S3** in production; MinIO is the local/dev/test
S3-compatible backend. `MinioService` (S3 SDK, path-style) and presigned URLs work
identically against both, so nothing here is MinIO-specific.

## 4. Contracts

Add to `packages/contracts/src/screenshot.ts` — the **upload metadata** (the image is the
file part, not in the schema):

```ts
export const UploadScreenshotMetaSchema = z.object({
  id: z.uuid(), // client-minted UUIDv7 → idempotency key
  timestamp: z.iso.datetime(), // capture time — also the partition key
});
export type UploadScreenshotMeta = z.infer<typeof UploadScreenshotMetaSchema>;
```

`timestamp` is client-supplied because it is half the composite PK `[id, timestamp]` and
drives monthly partitioning; the server cannot substitute receipt time without breaking
idempotent retry (a retried upload must land on the same partition + PK).

Extend `ScreenshotSchema` read fields (both optional, present only on reads):

```ts
url:     z.url().optional(),  // presigned thumbnail GET (grid) — READY rows only
fullUrl: z.url().optional(),  // presigned full-res GET — READY rows with a raw object
```

`blurred`, `status`, `redactedReason`, `storageKey`, `thumbnailKey` already exist.

## 5. API — `POST /screenshots` (multipart, streamed)

- Register `@fastify/multipart` in `apps/api/src/main.ts` with limits: **1** file,
  **10 MB** cap, accept **`image/png` + `image/jpeg`** only. Reject others → 415/422 via
  the problem+json filter.
- Controller consumes the file part as a stream + the text fields (`id`, `timestamp`),
  validates the metadata through `UploadScreenshotMetaSchema` (Zod), then hands the
  stream to the service.
- **Client contract (binds 2.2b):** the `id` and `timestamp` form fields **MUST precede the
  file part** in the multipart body. `@fastify/multipart`'s `req.file()` resolves when the
  file part is reached and only exposes fields parsed _before_ it — a client that sends the
  file first would yield `undefined` metadata → 422 on every valid upload. The 2.2b Swift
  uploader must emit the two text fields, then the image, in that order.
- **Size cap is enforced mid-stream:** if the 10 MB `fileSize` limit truncates the part, the
  handler treats it as a failed upload (`part.file.truncated`) and returns 413 — it does not
  write a `PENDING` row for a half-stored object.
- Service streams to storage via `lib-storage` `Upload` (no full buffer). Key layout:

  ```
  raw/<userId>/<id>     ← original upload
  thumb/<userId>/<id>   ← worker-generated derivative (see §7)
  ```

- **Owner is the session, never a body field:** `userId = session.userId`.
- **Upsert** the row on the PK → `status = PENDING`, `storageKey = raw/<userId>/<id>`,
  `blurred = false`, `thumbnailKey = null`. Re-uploading the same `id` overwrites the
  object and is a no-op on the row (idempotent — the client deletes local only after 201,
  so a lost-201 retry is expected and must not error or duplicate).
- Enqueue `screenshot-process` with `{ id, timestamp }` (the partition-qualified key).
- Return **201** with the storage key.

Ordering: object write → row upsert → enqueue → 201. If the row write fails after the
object is stored, the object is a harmless orphan (retry overwrites it); if enqueue fails
after the row is written, the row stays `PENDING` and a re-upload re-enqueues — no data
loss, no partial success returned as 201 without a row.

## 6. Worker — `screenshot-process`

Input `{ id, timestamp }`. Load the `PENDING` row (by PK) + the owning team's
`screenshotBlur` (join user → team, parse `Team.settings` with `TeamSettingsSchema`).
Download the raw object, process with `sharp`, then per policy:

| `screenshotBlur` | Raw object                              | Thumbnail (`thumb/<userId>/<id>`) | row `blurred` |
| ---------------- | --------------------------------------- | --------------------------------- | ------------- |
| `NONE`           | kept as-is                              | downscaled                        | `false`       |
| `BLUR`           | **overwritten with a blurred full-res** | blurred downscale                 | `true`        |
| `THUMBNAIL_ONLY` | **deleted from storage**                | downscaled                        | `false`       |

Then set `thumbnailKey`, `blurred`, `status = READY` on the row.

Rationale (confirmed): `BLUR` replaces the raw so **no unblurred full-res is ever
retained**; `THUMBNAIL_ONLY` deletes the raw so only a small thumbnail persists. Thumbnail
long edge ~320px (grid-sized). Idempotent: re-processing the same PK re-derives and
re-sets `READY` safely (overwrites derivatives). A row already `REDACTED` when the job
runs is skipped (redact may have raced ahead).

## 7. Storage key layout

`raw/<userId>/<id>` and `thumb/<userId>/<id>` — deriving both from `(userId, id)` keeps the
worker stateless (no need to persist a raw key beyond the row). Keys are opaque and never
public; all access is via short-lived presigned GETs.

## 8. API — `GET /screenshots` (reads, presigned)

Unchanged scoping (`@ResourceScope` self / manager-of-team / admin). For each row the
service adds presigned URLs (5-min TTL, `MinioService.presignGet`):

- `READY` → `url` = presigned `thumbnailKey`; `fullUrl` = presigned `storageKey` **iff a
  raw object exists** (absent for `THUMBNAIL_ONLY`).
- `PENDING` → neither URL yet.
- `REDACTED` → **never** a URL (objects are gone; the row is a tombstone).

Presigning is per-row in-process (no extra round trip to storage — `getSignedUrl` is a
local signing op). An employee viewing their own images gets `fullUrl` for full-res
transparency; the grid uses `url`.

## 9. API — `POST /screenshots/:id/redact`

- **Owner-only — NOT `@ResourceScope`** (that would let a manager redact). The route
  carries no `@ResourceScope`; the service loads the row (findFirst by `id` — the PK needs
  `timestamp`, which the route doesn't have) and asserts `row.userId === session.userId`,
  else **403**. A manager/admin redacting an employee's screenshot is exactly what PRD §6.2
  forbids.
- In one transaction: set `status = REDACTED` + `redactedReason = reason`, **delete the
  storage objects** (raw if present + thumb), write an `AuditLog` row
  (`action: 'screenshot.redact'`, actor = owner, target = screenshot) — CLAUDE.md: user-data
  mutations are audited.
- The **row persists** as a tombstone → the manager sees "redacted by employee: \<reason\>",
  never a silent disappearance (PRD §6.2). Object deletion happens after the row update
  commits (a failed delete leaves an orphan object, not an un-redacted row — fail safe
  toward privacy: the row already says REDACTED and reads never presign it).
- Redacting an already-`REDACTED` row is a no-op returning the tombstone (idempotent).
- 404 if no row with that `id` is visible; ownership check runs before revealing existence.

## 11. Testing

Harness:

- Add an **opt-in MinIO Testcontainer** to `db-harness.ts` (like Redis): start
  `minio/minio`, expose the API port, set `S3_ENDPOINT`/keys/bucket env for the run.
- **Remove** the `src/infra/storage/**` exclusion in `apps/api/vitest.coverage.config.ts`
  ([[api-coverage-gate]]) — the path is now exercised and must clear the 80% functions gate.

Integration cases (Vitest + Testcontainers, real Postgres + MinIO; **do not mock Prisma or
the S3 client**):

1. Upload a PNG → 201 + storage key; a `PENDING` row exists; the object exists in MinIO.
2. Duplicate `id` re-upload → 201, still one row (upsert no-op), object overwritten.
3. Worker `NONE` → `READY`, `thumbnailKey` set, thumb object exists, raw kept, `blurred=false`.
4. Worker `BLUR` → `READY`, `blurred=true`, raw object replaced (bytes differ), thumb exists.
5. Worker `THUMBNAIL_ONLY` → `READY`, raw object **gone**, thumb exists, `blurred=false`.
6. Read returns presigned `url` (+`fullUrl` when raw present); **never** a public URL;
   `PENDING`/`REDACTED` return no URL.
7. Redact by owner → row `REDACTED` + reason, objects deleted, `AuditLog` row written, row
   still listable as a tombstone.
8. Redact by a **manager** of the owner's team → **403** (owner-only). Redact of another
   team's shot → 403/404.
9. Reject non-image content-type and oversize upload.
10. Upload authz: the stored `userId` is the session user, not a spoofable body field.

Unit (no DB): metadata Zod parse (bad `id`/`timestamp` → 422); blur-mode → derivative-plan
mapping if that logic is factored into a pure function.

## 12. Boundaries / policy compliance

- `PrismaClient` stays in `*.repository.ts` (api) and the worker processor only.
- No raw image bytes ever logged (Pino); log `{ id, userId, status }` only.
- Screenshots remain employee-readable (PRD §4.3 / CLAUDE.md §1): the same `GET` the
  manager uses is self-scoped for the employee, and `fullUrl` gives them full-res.
- No capture path here (that's 2.2b behind `AckGate`); this slice only receives + stores.
- All routes under `/v1`, deny-by-default guard inherited; upload/redact are authenticated.
