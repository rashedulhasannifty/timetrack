# Slice 4.4 — SSO (OIDC) — Design

**Date:** 2026-07-24
**Roadmap:** `docs/plans/phase-4-sso-admin.md` Slice 4.4. **PRD:** §6.8.

## Goal

Let a user sign in through a configured OIDC identity provider (Google, Okta, Entra
ID, Auth0, Keycloak, …) and receive the **same** session everyone else gets — a normal
`TokenPair`, an httpOnly dashboard cookie — while email/password login keeps working
unchanged. Provisioning maps the IdP identity to the right `User` (team/role).

## Decisions

- **OIDC only.** SAML deferred to a later slice (build it only when a customer requires it).
- **Library:** `openid-client` (panva, v6) — the audited standard client (discovery, PKCE,
  state, nonce, JWKS/ID-token verification). One new **prod** dependency in `apps/api`.
  It is ESM-only and `apps/api` is CJS → it is loaded via dynamic `import()` (Node 24
  supports `require(esm)` too, but `await import()` is explicit and safe).
- **Provisioning:** link-by-verified-email **and** auto-provision new users.

## Architecture — split of responsibilities

The plan's literal wording put browser-facing `GET /auth/oidc/login` + `/callback`
redirects on the API. That fights two facts here: (1) the API cannot set the dashboard's
`tt_session` cookie (different secret; different origin in prod), so it would need a
Redis-backed one-time handoff-code subsystem to pass tokens back — and **the API has no
Redis client today**; (2) the dashboard BFF route is documented as _the ONLY place cookies
are written_.

So:

- **API `modules/auth` owns all OIDC crypto/protocol** — matching the plan's intent.
  `openid-client`, discovery, PKCE, code exchange, ID-token + nonce verification,
  provisioning, and token issuance all live here. IdP client secret never leaves the API.
- **Dashboard BFF owns browser redirects + cookies** — exactly as it already does for
  password login. State/nonce/PKCE live in a short encrypted httpOnly `tt_oidc` cookie,
  reusing the existing `session-cookie` AES-256-GCM pattern. No Redis, no handoff table,
  works across separate api/app domains in prod.

The API's two OIDC endpoints are `@Public` and **server-to-server** (called only by the
dashboard BFF), not browser-facing redirects.

### Flow

1. `/login` shows "Sign in with SSO" (only when SSO is configured), linking to dashboard
   `GET /api/auth/sso/start`.
2. Dashboard `GET /api/auth/sso/start` → calls API `POST /v1/auth/oidc/authorize` → API
   returns `{ authorizationUrl, state, nonce, codeVerifier }`. Dashboard encrypts
   `{ state, nonce, codeVerifier }` into the `tt_oidc` cookie (≈120s TTL, httpOnly,
   sameSite=lax) and 303-redirects the browser to `authorizationUrl`.
3. IdP authenticates → redirects to dashboard `GET /api/auth/sso/callback?code&state`.
4. Dashboard reads `tt_oidc`, checks `state` matches, then calls API
   `POST /v1/auth/oidc/callback { code, state, nonce, codeVerifier }`.
5. API exchanges the code with the IdP, verifies the ID token (issuer, audience, `nonce`,
   signature via JWKS), links-or-provisions the `User`, issues the same `TokenPair`,
   returns it.
6. Dashboard sets `tt_session`, clears `tt_oidc`, 303-redirects to `/`.

Failure at any step → dashboard clears `tt_oidc` and redirects to `/login?error=sso`.

## Contracts (`packages/contracts/src/auth.ts` or a new `oidc.ts`)

- `OidcAuthorizeResult` = `{ authorizationUrl: url, state, nonce, codeVerifier }`.
- `OidcCallbackRequest` = `{ code: string, state: string, nonce: string, codeVerifier: string }`.
- Reuse existing `TokenPair` for the response.

Types inferred from schemas; strict-mode body parsing via the shared pipe.

## Schema (migration in the same commit)

`packages/db/prisma/schema.prisma`, `User`:

- `passwordHash String` → `passwordHash String?` (SSO-only users have none).
- add `ssoProvider String?`
- add `ssoSubject String?`
- add `@@unique([ssoProvider, ssoSubject])`

Migration via `pnpm db:migrate`. **Regression-critical:** `AuthService.login()` must treat
a null `passwordHash` as invalid credentials (while still burning comparable argon2 time),
so an SSO-only account cannot be probed through the password path.

## Provisioning (`AuthService`)

On a callback identity `{ sub, email, emailVerified, name }`:

1. Find by `(ssoProvider='oidc', ssoSubject=sub)` → use it. This is the only branch that
   bypasses the email-verified gate, because `sub` is a stable IdP-issued identifier, not a
   user-controllable email.
2. **Fail-closed email gate (applies to BOTH link and provision):** require
   `emailVerified === true`. Treat an **absent** `email_verified` claim as `false` and
   reject. Without this, an IdP that emits an unverified `email: admin@company.com` would
   let an attacker be silently linked to an existing (possibly ADMIN) account —
   account takeover. The gate sits **above** the email branch, not inside auto-provision.
3. Find by `email`:
   - if found → **link** (backfill `ssoProvider`/`ssoSubject`), use it.
4. Else **auto-provision**: create `User` with `teamId = OIDC_DEFAULT_TEAM_ID`,
   `role = EMPLOYEE`, `passwordHash = null`, `ssoProvider='oidc'`, `ssoSubject=sub`,
   `name` from claim (fallback to email local-part).
5. Reject `deactivatedAt` users in every branch that resolves to an existing user
   (mirrors `refresh`).

`OIDC_DEFAULT_TEAM_ID` pointing at a nonexistent team would surface as a Prisma FK error
(500) on first provision. The repository create is wrapped so a `P2003` maps to a clean
`sso-misconfigured` problem+json (503), not a leaked Prisma error.

Then `issueTokens()` — the existing path, unchanged.

## Config (`packages/config` + `.env.example`, same commit)

All **optional** — unset ⇒ SSO disabled:

- `OIDC_ISSUER` (url)
- `OIDC_CLIENT_ID`
- `OIDC_CLIENT_SECRET`
- `OIDC_REDIRECT_URI` (the dashboard `…/api/auth/sso/callback` URL)
- `OIDC_DEFAULT_TEAM_ID` (uuid; the team new SSO users land in)

A refinement asserts they are all-set-or-all-unset. When unset: API OIDC endpoints throw
`NotFoundException` → a clean `404` problem+json (the routes read as absent), and the
dashboard hides the button.
Secrets never committed. `client_secret`/`code` confirmed absent from logs (add to the Pino
redact list if any structured log could carry them).

## Error handling

- API: all failures → RFC 9457 problem+json via the global filter; never leak IdP or
  `openid-client` internals. Invalid/expired code, nonce/state/issuer/audience mismatch,
  unverified email on auto-provision, deactivated user → 401 with a stable `type`.
- Dashboard: any non-200 from the API, a missing/mismatched `tt_oidc`, or a state mismatch
  → clear `tt_oidc`, redirect `/login?error=sso`.

## Testing

- **API unit (`auth.service.spec`)**: provisioning branches (new / link-by-email /
  reuse-by-subject), deactivated rejected, **unverified-email rejected on BOTH the link
  and provision paths**, absent `email_verified` claim rejected, password `login()` rejects
  a null-hash user. `openid-client` mocked at the module boundary.
- **API e2e (`auth.e2e-spec` or `oidc.e2e-spec`)**: `authorize` returns a valid URL +
  secrets; `callback` with a stubbed discovery/JWKS/token endpoint issues a real `TokenPair`
  and persists the `User`; bad state/nonce → 401; SSO-disabled → 404. A live
  IdP is a **manual** gate (plan's "validated against a real IdP"), not CI.
- **Dashboard (`route.spec`)**: `sso/callback` sets `tt_session` on API success; state
  mismatch and API failure both clear `tt_oidc` and bounce to `/login?error=sso`.

## Assumptions

- **Single-tenant, corporate IdP.** The email-verified link path trusts that the IdP owns
  its email namespace — correct for one company's Okta/Entra/Google-Workspace tenant.
  Pointing `OIDC_ISSUER` at a _consumer multi-tenant_ IdP would weaken this: `email_verified`
  there only proves mailbox ownership, so linking-by-email to a pre-existing privileged
  account becomes a vector. Do not configure such an IdP without disabling email linking.

## Out of scope

SAML; multi-IdP; SSO for the macOS client (browser/dashboard flow only this slice);
per-team IdP config; SCIM/deprovisioning.
