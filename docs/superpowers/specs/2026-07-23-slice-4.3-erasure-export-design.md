# Slice 4.3 — Right-to-erasure + export — design

**Phase:** 4 (SSO + admin + retention). **PRD:** §4.4 (right to erasure), §6.6 (admin).
**Plan slice:** `docs/plans/phase-4-sso-admin.md` §4.3.

**Goal:** an ADMIN can EXPORT a user's full data, then ERASE it — all their data rows hard-deleted
and their screenshot objects removed, the `users` row anonymized to a tombstone, recorded in
`audit_log`.

---

## 0. Starting point (what already exists)

- **Route already wired:** `admin.controller.ts:38-46` — `@Post('users/:id/erase') @HttpCode(204)`,
  body validated by `ZodValidationPipe(EraseUserSchema)`, class-gated `@Controller('admin')` +
  `@Roles('ADMIN')`. `admin.service.ts:35-38` `eraseUser` throws `NotImplementedException`;
  `admin.repository.ts:103-104` is a bare TODO comment.
- **`EraseUserSchema`** exists (`packages/contracts/src/admin.ts:47-53`): `{ reason: string 1..500 }`.
- **No export** anything: no route, no contract, no api-client method, no UI.
- **API object storage:** `apps/api/src/infra/storage/minio.service.ts` — has `putObject`,
  `putStream`, `presignGet`, and **single-key `deleteObject` only** (l.73). No batch/prefix delete.
  Batch `deleteObjects` exists only on the worker (`apps/worker/src/infra/s3.provider.ts:53`), and
  apps may not import each other.
- **Screenshot object keys are user-prefixed** — `raw/${userId}/${id}`
  (`screenshots.service.ts:51`) and `thumb/${userId}/${id}`
  (`screenshot-process.processor.ts:53`). **Both derivable from the userId alone.**
- **Export precedent (the only file-download chain in the repo):** `StreamableFile` +
  `AsyncIterable` generator + keyset-paginated `streamEntries` (`reports.controller.ts:47-59`,
  `reports.service.ts:84-101`, `reports.repository.ts:215+`) → dashboard `getRaw`
  (`api-client.ts:115-120`) → Route Handler piping the body
  (`app/(app)/reports/export/route.ts`).
- **Destructive-action-with-reason UI precedent:** there is **no** modal/dialog primitive in the
  dashboard. The established pattern is inline disclosure — `me/ScreenshotsPanel.tsx:72-110`
  (local `open` state → reason input, amber warning, Confirm disabled until reason non-empty,
  Cancel, inline error).
- **Audit + transaction idiom:** `users.repository.ts:72-110` `setActive` (multi-table write +
  token revoke + `auditLog.create`, all in one `$transaction`, with a `SELECT … FOR UPDATE`
  last-admin guard at l.81-85).

### Every table holding this user's data

| Table                      | User column                      | FK to `users`?             | Index serving `WHERE userId`   | Partitioned |
| -------------------------- | -------------------------------- | -------------------------- | ------------------------------ | ----------- |
| `refresh_tokens`           | `userId`                         | YES (`ON DELETE RESTRICT`) | `@@index([userId])`            | no          |
| `time_entries`             | `userId` (+ `editedById`, no FK) | YES (RESTRICT)             | yes                            | no          |
| `timesheet_approvals`      | `userId` (+ `reviewerId`, no FK) | YES (RESTRICT)             | yes                            | no          |
| `activity_samples`         | `userId`                         | **no FK**                  | `@@index([userId, timestamp])` | **monthly** |
| `screenshots`              | `userId`                         | **no FK**                  | `@@index([userId, timestamp])` | **monthly** |
| `idle_events`              | `userId`                         | **no FK**                  | `@@index([userId, startTime])` | no          |
| `activity_daily_summaries` | `userId`                         | **no FK**                  | PK `@@id([userId, day])`       | no          |
| **`invites`**              | **`email`** (NOT userId)         | no                         | `@@index([email])`             | no          |
| `audit_log`                | `actorId` / `targetId`           | no FK                      | —                              | no          |

Two consequences that drive the design:

1. **No cascade exists anywhere** (every User FK is `ON DELETE RESTRICT`; four tables have no FK
   at all). Every table must be deleted explicitly.
2. **`invites` is keyed by `email`, not `userId`** — it stores the user's real `name` and `email`
   and is invisible to any userId-based sweep. Missing it means PII survives "erasure". It is in
   the deletion set, matched by the user's real email captured **before** anonymizing.

Every user-owned table already has a `userId`-leading index, so a per-user `DELETE` is index-served
on every table (including across the monthly partitions). **No new index or migration is needed.**

## 1. Decisions (settled during brainstorming)

1. **The `users` row is ANONYMIZED to a tombstone, not deleted.** All their _data_ rows are
   hard-deleted. Keeping a scrubbed row means the plain-string references that other users' rows
   hold (`time_entries.editedById`, `timesheet_approvals.reviewerId`, `audit_log.actorId`) still
   resolve instead of dangling, while no PII remains.
2. **Erase runs SYNCHRONOUSLY: S3 objects first, then one `$transaction`.** Object keys are
   derivable from the userId, so the sweep needs no DB read and is idempotent. Any S3 failure
   aborts before a single row is touched — retention's proven rule (`never drop a row while its
object could survive`). Realistic volumes (~40k activity rows, ~9k objects for a 90-day user)
   are well within a request; no queue is introduced.
3. **Export is streamed JSON, metadata only.** Uses the existing `StreamableFile` + generator +
   keyset-streaming chain. No new dependency (a zip would need one). Screenshot image bytes are
   not bundled; their metadata (including `storageKey`) is.
4. **Historical `audit_log` rows are kept untouched** — including diffs that may embed the user's
   content (e.g. a `time_entry.edit` row's `{before, after}` note text). The trail stays intact and
   tamper-evident, as PRD §4.4 requires deletions be recorded. **This is an accepted, documented
   residual of erasure**, not an oversight.

## 2. Erase — `POST /v1/admin/users/:id/erase` → 204

### Order of operations (the ordering IS the compliance property)

```
1. Service: load target user (id, email, teamId, role, deactivatedAt).
   → 404 if not found.
2. Service: LAST-ADMIN PRE-CHECK (cheap read) → refuse BEFORE touching S3.
3. Service: S3 prefix sweep — delete raw/<id>/  and  thumb/<id>/
   → ANY failure: throw, abort. Nothing DB-side has changed. Idempotent on re-run.
4. Repository: ONE $transaction:
     a. re-assert last-admin under SELECT … FOR UPDATE   (authoritative, race-safe)
     b. deleteMany each user-owned table, capturing per-table counts
     c. deleteMany invites WHERE email = <captured real email>
     d. update users row → tombstone
     e. auditLog.create({ action:'user.erase', diff: <counts only> })
5. → 204
```

**Why objects before rows.** If the sweep succeeds but the transaction fails or the process
crashes, nothing DB-side changed: the PII rows are intact and the operation is simply re-run (the
prefix sweep no-ops on already-deleted keys). There is no committed state in which a live
`screenshots` row points at a deleted object, because row deletion happens inside the same
transaction as everything else.

**The narrow race.** Between the step-2 pre-check and the step-4a re-check, another admin could be
deactivated, making the target the last admin. The transaction then refuses — after the objects
were swept. That leaves the user's rows intact but their screenshot objects gone: a strictly
_less_ PII-exposed state than the alternative, and fully recoverable (re-running erase once the
admin situation is resolved completes it). Accepted.

### `MinioService.deleteByPrefix(prefix: string): Promise<number>`

New method on the API's storage service (`@aws-sdk/client-s3` is already a dependency — no new
dep). Paginates `ListObjectsV2` under the prefix and issues `DeleteObjects` in batches of ≤1000,
returning the count deleted. Throws if any key reports an error, so the caller aborts — mirroring
`WorkerS3.deleteObjects` (`s3.provider.ts:53-66`). The two prefixes swept are `raw/<userId>/` and
`thumb/<userId>/`.

### The transaction's deletion set

`refresh_tokens`, `time_entries`, `timesheet_approvals`, `activity_samples`, `screenshots`,
`idle_events`, `activity_daily_summaries`, `invites` (by email). Each `deleteMany` returns a
`count`, collected into the audit diff.

**Refresh tokens are hard-deleted, not just revoked.** The existing `setActive` path only sets
`revokedAt`; erasure removes the rows (they are per-device artifacts of the erased user).

### The tombstone

```
email           → `erased-${userId}@erased.invalid`   // .invalid is RFC-2606 reserved: can never
                                                      // collide with a real address, and `email`
                                                      // is @unique so it must be per-user
name            → 'Erased user'
passwordHash    → a fixed non-verifying sentinel
monitoringAckAt → null      // PRD §4.1 — null means monitoring MUST NOT run
deactivatedAt   → now()     // login is already refused for a deactivated user
```

Implementation must confirm the login path rejects a deactivated user **before** it attempts an
Argon2 verify, so a sentinel `passwordHash` can never reach the verifier and surface as a 500
instead of a 401. If it does not, the sentinel must instead be a valid Argon2 hash of an
unguessable random value.

### The audit row — counts only

```ts
auditLog.create({
  actorId: actor.id,
  action: 'user.erase',
  targetType: 'user',
  targetId: userId,
  diff: { reason, deleted: { timeEntries: n, activitySamples: n, screenshots: n, … }, deletedObjects: n },
});
```

**The diff must never contain the erased email, name, or a before-snapshot.** Writing the old PII
into an audit row we keep forever would re-record exactly what we just erased. Counts + the
admin-supplied `reason` only. (The diff object must be declared as a `type` alias, not an
`interface` — Prisma's `InputJsonValue` needs the implicit index signature.)

### Guards

- **Last active admin** — refuse. Erase is strictly more destructive than deactivate, which
  already guards this (`users.repository.ts:81-85`, `SELECT … FOR UPDATE`). Erasing the last
  active admin would lock the team out permanently and irreversibly. Mirror that guard's shape and
  return a distinct result the service maps to a 409-style problem+json.
- **Self-erase is REFUSED (409)** — mirroring the existing self-deactivation guard
  (`users.service.ts:53-59`, "You cannot deactivate your own account"). Erase is strictly more
  destructive, and an admin destroying their own account mid-request (deleting the very tokens
  authenticating it) is the same foot-gun. An admin who wants their own data erased is erased by
  another admin.
- **Cross-team is REFUSED (403)** — see §4.
- **404** when the target user does not exist.

Guard order (all before any S3 or DB write): 404 → cross-team 403 → self-erase 409 → last-admin 409.

## 3. Export — `GET /v1/admin/users/:id/export`

New endpoint on `AdminController`. Returns a `StreamableFile`, `application/json`,
`disposition: attachment; filename="timetrack-user-<id>-export.json"`.

**Key invariant: the export covers every table the erase destroys, with one deliberate exception —
`refresh_tokens`.** Those rows are auth artifacts, not personal data, and `tokenHash` is live
session material; handing it to an admin in a download would be a security regression. Everything
else in the deletion set appears, plus the audit rows about the user. That makes the export
provably complete with respect to the personal data erasure destroys, and it is asserted as such
in the tests.

```jsonc
{
  "exportedAt": "2026-07-23T…Z",
  "user": { id, email, name, role, teamId, monitoringAckAt, deactivatedAt, createdAt },
  "timeEntries":            [ … ],
  "timesheetApprovals":     [ … ],
  "activitySamples":        [ … ],   // large — streamed
  "activityDailySummaries": [ … ],
  "screenshots":            [ … ],   // metadata incl. storageKey/thumbnailKey; no image bytes
  "idleEvents":             [ … ],
  "invites":                [ … ],   // matched by email
  "auditLog":               [ … ]    // actorId = id OR (targetType='user' AND targetId = id)
}
```

**Streaming, not buffering.** The service returns an `AsyncIterable<string>`; the generator emits
the JSON envelope incrementally and delegates each large table to a keyset-paginated repository
generator (batch 500), mirroring `reports.repository.streamEntries`. `activity_samples` can be
tens of thousands of rows — it must never be materialized in memory.

`activity_samples.windowTitle` **is** included: it is the subject's own data and PRD §"symmetric
transparency" entitles them to it. This is an export, not a log — CLAUDE.md's ban is on _logging_
`windowTitle`, which this must continue to respect (never log the export payload).

## 4. Authorization

Both routes inherit the class-level `@Controller('admin')` + `@Roles('ADMIN')` and the global
`RolesGuard`.

**Both routes are additionally TEAM-SCOPED: `target.teamId !== actor.teamId` → 403.**

The repo draws a deliberate distinction between two different rules, and erase/export fall under
the second:

- **Reading a user's data** goes through `ResourceAccessService.assertCanAccessUser`
  (`common/authz/resource-access.service.ts:23`), which grants `ADMIN → any user`. That is the
  rule `@ResourceScope` applies.
- **Administering a user** is team-scoped. `users.service.ts:47-52` — the closest existing
  analogue to erase — rejects managing a user outside the actor's team:
  `if (target.teamId !== actor.teamId) throw ForbiddenException('Cannot manage a user in another team')`.

Erase is unambiguously an administration operation (strictly more destructive than deactivate),
and export hands over another user's entire data set, so **both inherit the team check** rather
than the `ADMIN → any user` data-read rule. This is the explicit CLAUDE.md §8.6 reason for not
using the stock `@ResourceScope`: the standard self/manager/admin policy is wrong here (a user
must not reach their own erase via the "self" branch, and ADMIN must not reach across teams). The
check is bespoke and lives in the service, mirroring `users.service.setActive`.

**Required tests:** the cross-team 403 (an admin of team A erasing/exporting a team B user), not
just the non-admin 403.

The 403 path is asserted with the established metadata idiom —
`Reflect.getMetadata(ROLES, AdminController)` equals `['ADMIN']` (with `import 'reflect-metadata'`),
matching `projects.controller.spec.ts` — since this repo has no HTTP-level e2e harness.

## 5. Dashboard

`(app)/admin/users` — extend the existing row actions.

- **`api-client.ts`:** `eraseUser(token, id, dto)` via `send('POST', …)`; `exportUserData(token, id)`
  via `getRaw` (streams, no schema parse — same as `exportReportCsv`).
- **Export download:** a Route Handler at `(app)/admin/users/[userId]/export/route.ts` that checks
  the session + ADMIN role, calls `api.exportUserData`, and pipes `upstream.body` through with the
  upstream `content-type`/`content-disposition` + `cache-control: no-store` — mirroring
  `reports/export/route.ts`. The bearer token never reaches the browser.
- **Erase UI:** extend `UserRowActions.tsx` with the inline-disclosure destructive pattern copied
  from `ScreenshotsPanel.tsx:72-110` — an "Erase…" button reveals a required reason input
  (`maxLength 500`), an explicit irreversible-action warning naming the user, Confirm (disabled
  until the reason is non-empty) and Cancel, with the `ApiError` message surfaced inline. Plus an
  "Export" link to the Route Handler.
- **`actions.ts`:** `eraseUserAction(prev, formData)` — re-checks `session.role === 'ADMIN'`,
  parses the reason with `EraseUserSchema`, calls the API, `revalidatePath('/admin/users')`,
  returns `{ ok }` / `{ ok:false, message }` from `ApiError`.

## 6. Testing

- **DISCRIMINATING completeness e2e:** seed a user with rows in **every** user-owned table (incl.
  an `invites` row for their email) plus objects in MinIO, run erase, then **enumerate every table
  and assert 0 rows remain for that user**, that the `users` row is a tombstone, and that both S3
  prefixes are empty. A test that checks three tables passes while PII survives in the ninth —
  this test exists specifically to catch an `Invite`-class miss.
- **S3-abort e2e:** a failing sweep leaves **every** row intact and no tombstone; a healthy re-run
  completes the erase.
- **Last-admin refused:** erasing the only active admin performs no writes and no object deletion.
- **Audit row:** written in the same transaction, `action: 'user.erase'`, and the diff contains
  counts + reason and **no email/name** (assert the serialized diff does not contain the erased
  address).
- **Export completeness:** the exported JSON contains a non-empty array for every table the erase
  set deletes (the invariant), streams without buffering, and includes the `invites`/`auditLog`
  sections.
- **Authz refusals (each performs NO writes and NO object deletion):** cross-team 403,
  self-erase 409, last-admin 409, unknown user 404, and the non-admin 403 (metadata assertion).
  Unit tests for controller delegation.
- Integration tests use Testcontainers (real Postgres 18 + MinIO), never a mocked Prisma.

## 8. Constraints (binding, from CLAUDE.md)

- Prisma only in `admin.repository.ts`; controller/service stay Prisma-free. `select` explicit.
- Deletes on user data must write an `AuditLog` row **in the same transaction** — satisfied by §2.
- No new dependency, no new env var, no schema change (no migration this slice).
- Never log `windowTitle`, screenshot bytes, secrets — or the export payload / erased PII.
- Zod-only validation, types inferred. Pipe scoped to the parameter.
- New endpoint (`export`): documented reason for no `@ResourceScope` (§4) + the 403 test.
- Commits: Conventional Commits, scope ∈ {api, dashboard}, **no AI attribution**, author = repo
  git user.
