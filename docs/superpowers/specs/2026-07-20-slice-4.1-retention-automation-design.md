# Slice 4.1 — Retention automation (design)

**Phase 4 — SSO + admin + retention.** First slice: the compliance backbone.

**PRD:** §10 (data retention), §7.3 (monthly partitions).
**Plan:** `docs/plans/phase-4-sso-admin.md` → Slice 4.1.

**Goal:** enforce retention by a nightly job, not by policy prose. Expired
screenshot/activity data is removed with an audit trail; retention floors (already
enforced in `TeamSettingsSchema`) are respected; no unbounded `DELETE`.

**Done when:** a nightly job drops fully-expired monthly partitions, hard-deletes the
per-team stragglers in still-live partitions, deletes the corresponding S3/MinIO objects
first, and writes one `AuditLog` row per run with counts — all integration-tested.

---

## 1. The core problem — global partitions vs per-team retention

The two high-volume tables are **globally partitioned by month** on `timestamp`
(`activity_samples_YYYY_MM`, `screenshots_YYYY_MM` — see the init migration and
`partition.util.ts`). A single partition (e.g. `screenshots_2026_07`) holds **every
team's** rows for that month.

Retention, however, is **per team**, from `Team.settings` (validated by
`TeamSettingsSchema`):

- `screenshotRetentionDays` — default 30, floor 1, max 180.
- `activityRetentionDays` — default 90, floor 7, max 365.

So we cannot naively "DROP the expired partition for a team": one team's data in that
partition may still be within its retention while another's has expired.

### The model: DROP + bounded straggler DELETE (hybrid)

For each partitioned table, per run (`now = job time, UTC`):

1. **Compute `maxRetentionDays`** = the maximum of that table's retention field across
   **all** teams (screenshots → `screenshotRetentionDays`; activity → `activityRetentionDays`).
   Fall back to the schema default if a team has no explicit value (parsing through
   `TeamSettingsSchema` supplies it). If there are no teams, skip.
2. **DROP whole partitions** whose entire date range is older than
   `now − maxRetentionDays`. A partition `[from, to)` is droppable iff `to <= cutoffMax`
   where `cutoffMax = now − maxRetentionDays`. This is the fast path — `DROP TABLE`, no scan.
   It only fires once a month's data is past the **longest** team's retention.
3. **Bounded straggler DELETE** for teams with **shorter** retention whose expired rows
   still live in a not-yet-droppable partition. For each team:
   `DELETE FROM <table> WHERE userId IN (team's user ids) AND timestamp < (now − team.retentionDays)`
   — bounded (per team, and only rows above each team's own cutoff), never a full-table sweep.
   The partitioned tables carry only `userId` (no `teamId`), so straggler deletion is
   naturally "resolve each team's users, delete their expired rows."

**Why both are required:** DROP alone would silently grant every team the _longest_
team's retention — the exact "screenshots forever" compliance miss this slice exists to
prevent. The straggler DELETE is what actually enforces short-retention teams, and for a
mixed fleet it is the path that fires every night for months. DROP is the cheap win once a
whole month is universally expired.

> `ActivitySample` and `Screenshot` declare no inbound foreign key / Prisma relation, so
> `DROP TABLE <partition>` is clean (no dependent-row cascade), keeping it a fast metadata op.

## 2. S3/MinIO object cleanup — order and failure policy

Screenshot object keys live **only in the DB rows** (`storageKey = raw/{userId}/{id}`,
`thumbnailKey = thumb/{userId}/{id}`). The key encodes no date, and `WorkerS3` has no
`listObjects`. Therefore objects must be found **from the rows that are about to die** and
deleted **before** the DB rows disappear. (Activity samples have no objects — DB only.)

**Order per unit of work (one partition, or one team's straggler batch):**

1. Select the `storageKey` + non-null `thumbnailKey` of the rows in scope
   (for a DROP: all rows in the partition; for a straggler DELETE: the team's expired rows).
2. Batch-delete those objects via a new `WorkerS3.deleteObjects(keys[])`
   (S3 `DeleteObjects`, ≤1000 keys/call, chunked). Empty keys (`storageKey === ''`, set when
   a `THUMBNAIL_ONLY` raw was already removed) are filtered out.
3. **Only if all object deletes for that unit succeed**, perform the `DROP TABLE` /
   `DELETE`.

**Failure policy — abort-that-unit-and-retry (chosen for compliance):** if any object
delete in a unit fails, **skip** the DROP/DELETE for that unit this run, log the failure,
and note it in the audit `diff` as deferred. The next nightly run retries. This guarantees
a DB row is never removed while its S3 object survives — since the row is the _only_ holder
of the object key, dropping the row first would orphan the bytes irrecoverably. A unit that
defers does not block other units (other partitions/teams still process).

## 3. Wiring

### 3.1 `WorkerS3.deleteObjects(keys: string[])`

New batched delete on `apps/worker/src/infra/s3.provider.ts`. Uses
`DeleteObjectsCommand`, chunks to ≤1000 keys/request, ignores empty strings. Throws if the
delete reports errors (so the caller can honor the abort-and-retry policy). Existing single
`deleteObject` stays.

### 3.2 `RetentionCleanupProcessor` (`@Processor('retention')`)

Replaces the scaffold. `process()`:

- For each partitioned table (`screenshots`, `activity_samples`):
  - resolve `maxRetentionDays` across all teams (parse each `Team.settings` via
    `TeamSettingsSchema`);
  - enumerate that table's partitions (`pg_inherits`/`pg_class`, or the
    `{table}_YYYY_MM` naming) and their bounds; DROP the ones fully past `cutoffMax`
    (screenshots: collect+delete objects first, per §2);
  - for each team, straggler-DELETE rows past that team's own cutoff still in live
    partitions (screenshots: objects first).
- Write **one** `AuditLog` row: `actorId = SYSTEM_ACTOR_ID`, `action = 'retention.cleanup'`,
  `targetType = 'system'`, `targetId = 'retention'`, `diff =` per-table counts
  (`droppedPartitions`, `deletedRows`, `deletedObjects`, and any `deferred` units with reasons).

Pure date/partition math (compute cutoffs, decide which `{table}_YYYY_MM` are droppable
from their bounds) goes in a unit-testable helper (extend `partition.util.ts` or a sibling
`retention.util.ts`), mirroring how `partition.util.ts` is unit-tested without a DB.

### 3.3 `SYSTEM_ACTOR_ID`

`AuditLog.actorId` is a plain string in the DB, but the read contract
`AuditLogEntrySchema.actorId` is `z.uuid()` (Slice 4.2 audit UI parses it). A `"system"`
string would break that UI. So the system actor is the **nil UUID sentinel**
`00000000-0000-0000-0000-000000000000`, defined once as a shared constant
(`packages/contracts`, alongside `admin.ts`) and reused by any future system-written audit
row.

### 3.4 `RetentionScheduler` (`OnApplicationBootstrap`)

Mirrors `RollupScheduler`/`TimesheetScheduler`. Registers a nightly repeatable job that
enqueues **both** `retention` **and** `partition-provision`. Rationale:
`partition-provision` is registered as a queue+processor today but **is never scheduled** —
without provisioning, inserts into next month's range fail. This slice is where nightly
provisioning finally gets turned on, alongside retention.

- `retention` — nightly, e.g. `20 3 * * *` UTC (after the day's data settles, off-peak).
- `partition-provision` — nightly (idempotent DDL; safe to run every night), enqueued from
  the same scheduler so next month's partition always exists before retention/inserts need it.

Register the provider in `worker.module.ts`.

## 4. Testing (integration — real Postgres + MinIO)

Reuse `apps/worker/test/worker-harness.ts` (`startWorkerEnv`) and the `RUN_E2E=1` gate.
New spec `apps/worker/test/retention-cleanup.e2e-spec.ts`:

1. **Centerpiece — mixed retention, shared partition:** two teams in the _same_ live
   partition, retentions 7 vs 90 days; seed rows straddling both cutoffs → run → the
   partition **survives**, team-7's expired rows are **gone**, team-90's rows **kept**, the
   audit row counts both. This is the proof the hybrid is correct.
2. **DROP path:** synthesize an old partition (`migrate deploy` only creates `2026_07`+, and
   you can't insert into an unpartitioned range) — create e.g. `screenshots_2025_12` via the
   partition DDL, insert rows older than every team's retention + seed their S3 objects → run
   → the partition table is **dropped** and its objects are **deleted**.
3. **S3 abort-and-retry:** force an object-delete failure for a unit → that unit's rows are
   **not** dropped/deleted this run and the audit `diff` records it deferred; a second run
   with S3 healthy completes it.
4. **Floors respected / no unbounded delete:** rows within retention are untouched; the
   straggler `DELETE` is scoped to a team's users and its own cutoff.
5. **Audit + system actor:** one `AuditLog` row per run, `actorId === SYSTEM_ACTOR_ID`
   (valid `z.uuid()`), counts present.

Plus unit tests for the new `retention.util` helpers (cutoff math, droppable-partition
decision from bounds) and for `WorkerS3.deleteObjects` chunking (≤1000). Scheduler test
mirrors the existing scheduler specs (asserts both jobs registered).
