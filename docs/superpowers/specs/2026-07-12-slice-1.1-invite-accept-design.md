# Slice 1.1 — Bootstrap + invite/accept (self-serve auth)

**Status:** design approved (2026-07-12)
**Plan:** `docs/plans/phase-1-mvp.md` Slice 1.1 · builds on Slice 1.0 (seed admin + Testcontainers harness)

## Goal

An ADMIN invites a user by email; the invitee sets their own Argon2id password via a one-time token and is auto-logged-in. The Slice 1.0 seed admin is the bootstrap — no hand-inserted rows.

## Non-goals

- **No `AuditLog` writes** — deactivate/settings audit is Slice 1.2.
- **No full Nest-app-boot HTTP e2e** — that harness is assigned to Slice 1.4. Slice 1.1 proves correctness at the service + real-DB integration level plus a manual HTTP smoke.
- No SMTP — `EmailProcessor` logs the `invite` job; real sending is later.
- No dashboard UI — invite/accept screens are Slice 1.2/1.5. This slice is API + contracts + schema.

## Decisions (resolved)

- **Create user on accept, not at invite.** `User.passwordHash` is NOT NULL, so invite time persists only an `Invite` row; `accept` CREATEs the `User`. This resolves the plan's internal inconsistency (it says accept "sets User.passwordHash" while also preferring a separate `Invite` to keep passwordHash non-null). Two forced deviations from the plan's `Invite` sketch: (1) `Invite` carries `name` (needed to materialize the user; admin supplies it via `InviteUserSchema`); (2) accept _creates_ rather than _updates_ a user.
- **Token hashing: plain SHA-256, no new env.** Token = 256-bit random (`randomBytes(32).base64url`), stored as `tokenHash = sha256(token)`. The token is already unguessable, so hashing only needs to defeat a DB-hash-leak replay — SHA-256 suffices. Deliberately NOT the refresh-token HMAC idiom (which exists to make a stolen DB hash useless without `JWT_REFRESH_SECRET`); invites are 72h, single-use, lower value, and this avoids an `INVITE_TOKEN_SECRET` env. (Documented to preempt an "inconsistent with refresh tokens" review note.)
- **Enqueue failure is fatal to the invite.** Postgres (invite row) and Redis (email job) can't share a transaction. Commit the invite, then enqueue; if enqueue throws, the request fails (500) — a silently undelivered invite is worse than a retryable error.
- **Invite expiry = 72h**, a `INVITE_TTL_HOURS = 72` constant (no new env).
- **No new env vars this slice** (`REDIS_URL` already exists).

## Components

### 1. Schema — `packages/db/prisma/schema.prisma` + migration (same commit)

```prisma
model Invite {
  id         String    @id @default(uuid(7))
  email      String
  name       String
  role       Role      @default(EMPLOYEE)
  teamId     String
  team       Team      @relation(fields: [teamId], references: [id])
  tokenHash  String    @unique
  expiresAt  DateTime
  acceptedAt DateTime?
  createdAt  DateTime  @default(now())

  @@index([email])
  @@map("invites")
}
```

Add `invites Invite[]` back-relation to `Team`. Slice 1.0's dynamic `truncateAll` (reads `pg_tables`) covers the new table with no change.

### 2. Contracts — `packages/contracts`

- `auth.ts`: `AcceptInviteSchema = z.object({ token: z.string().min(1), password: z.string().min(8).max(200) })` (mirrors `LoginSchema`). Accept returns the existing `TokenPairSchema` (auto-login).
- `users.ts`: `InviteResultSchema = z.object({ invite: z.object({ id: z.uuid(), email: z.email(), role: Role, teamId: z.uuid(), expiresAt: z.iso.datetime() }), devToken: z.string().optional() })`. `devToken` is populated **only when `NODE_ENV === 'development'`** (strictly dev — not test, not staging) and is **never logged** (bearer secret).
- Both files are already `export *`'d by the barrel — no `index.ts` edit.

### 3. `modules/invites/` — one home for `Invite` Prisma access

Controller-less vertical slice; `InvitesModule` exports `InvitesService`.

- `invites.repository.ts` (Prisma only):
  - `createInvite({ email, name, role, teamId, tokenHash, expiresAt }): Promise<{ id, expiresAt }>`
  - `acceptInTransaction(tokenHash, passwordHash, now): Promise<AcceptedIdentity | null>` — ONE `$transaction`: find invite by `tokenHash`; if missing / expired / already accepted → return `null`; else conditional consume (`updateMany WHERE id = ? AND acceptedAt IS NULL` set `acceptedAt = now`, assert count === 1) and `user.create({ email, name, role, teamId, passwordHash })`; return `{ id, role, teamId, deactivatedAt: null }`. `User.email` unique is the race backstop (a duplicate throws → surfaced as invalid).
  - `emailExistsAsUser(email): Promise<boolean>`
- `invites.service.ts` (business logic; no Prisma):
  - `create(dto: InviteUser, actor: SessionUser): Promise<{ invite; token }>` — guard: `actor.role === 'ADMIN' && actor.teamId === dto.teamId` else 403 (defence beyond the `@Roles` gate); reject if `emailExistsAsUser` → 409 Conflict; mint token, `sha256`, persist, then **enqueue** `QUEUES.email` job `'invite'` with `{ email, name, inviteToken, expiresAt }`; return `{ invite, token }`.
  - `accept(token, password): Promise<AcceptedIdentity>` — `argon2.hash(password, { type: argon2.argon2id })`; call `acceptInTransaction(sha256(token), hash, now)`; `null` → throw 401 (invalid/expired/used). Returns the identity for AuthService to mint tokens.

### 4. Endpoints (unchanged locations)

- `users.controller.ts`: `invite` already exists — change its return to `Promise<InviteResult>`. `UsersService.invite(dto, actor)` calls `InvitesService.create`, maps to `InviteResult`, sets `devToken` only when `NODE_ENV === 'development'`. `UsersModule` imports `InvitesModule`.
- `auth.controller.ts`: add `@Post('accept-invite') @Public() @HttpCode(200)` → `AuthService.acceptInvite(dto: AcceptInvite): Promise<TokenPair>` → `this.invites.accept(...)` then the existing **private** `issueTokens(identity)` (auto-login stays inside AuthService). `AuthModule` imports `InvitesModule`.

### 5. Email — `apps/worker` + redaction

- `EmailProcessor`: add an `'invite'` case that logs `{ jobId, email }` only (never the token). SMTP is later.
- `inviteToken` is a bearer secret → add `'*.inviteToken'` and `'inviteToken'` to `packages/logger` `REDACT_PATHS` **in the same commit** (CLAUDE.md §4).

### 6. Harness — `@testcontainers/redis` (the Slice 1.0 deferral)

Add `@testcontainers/redis` to `apps/api` devDeps. Extend `startTestDb(opts?: { redis?: boolean })`: when `redis: true`, start a Redis container, set `process.env.REDIS_URL`, and include it in `close()`. PG-only specs (existing) are unaffected and stay fast.

## Testing

- **Unit (Vitest, mocks):**
  - `InvitesService.accept`: success, expired → 401, already-accepted → 401 (repo returns `null`).
  - `InvitesService.create`: cross-team actor → 403, existing-email → rejected, happy path mints+enqueues.
  - `AuthService.acceptInvite`: delegates to `invites.accept` then `issueTokens` (mock `InvitesService`).
- **Integration (Testcontainers):**
  - `InvitesService.accept` against **real Postgres** (harness): accept once → user created + invite consumed; accept again → rejected (single-use, real conditional update); expired → rejected.
  - `InvitesService.create` against **real PG + Redis** (`startTestDb({ redis: true })`): invite persisted + job really enqueued (assert via a BullMQ `Queue`/`Worker` read).
- **Manual verify (HTTP smoke):** seed admin → `POST /v1/auth/login` → `POST /v1/users/invite` (capture `devToken`) → `POST /v1/auth/accept-invite` → `POST /v1/auth/login` as the new user.

## Done when

- An ADMIN can invite a user; the invitee accepts with a self-chosen password and is auto-logged-in; no manual DB writes.
- Token is single-use and expires (72h); reused/expired/invalid → 401.
- Invite guards enforce ADMIN + team ownership (403 tested) and reject an already-existing user email.
- `@testcontainers/redis` added; harness supports opt-in Redis; integration tests prove the transactional consume and the real enqueue.
- Gate green; `devToken` only in development and never logged; `inviteToken` in the redact list.
